## 3. Wiki에서 더 뽑을 수 있는 글감

상태: 후보 정리

목적: workflow wiki를 단순 문서 저장소가 아니라 "AI와 일하는 방식을 팀 지식으로 승격하는 장치"로 설명한다.

읽기 기준: 기술 문서 소개가 아니라, 디자이너가 자기 작업 기록을 어떻게 팀의 반복 가능한 기준으로 바꿀 수 있는지 보여준다.

| 우선순위 | 글감 | 추천 형태 | 메모 |
| --- | --- | --- | --- |
| 1 | Wiki는 worklog의 예쁜 버전이 아니다 | 단독 글 | raw 기록과 반복 지식의 차이를 설명하기 좋다. AX 4편과도 연결 가능 |
| 2 | 디자이너가 Storybook을 QA 공간으로 쓰는 법 | 단독 글 또는 AX 2편 보강 | "Figma랑 달라요"를 감으로 말하지 않고 상태별로 확인하는 방식 |
| 3 | Figma-first는 Figma-only가 아니다 | AX 2편 보강 또는 짧은 글 | 탐색은 code prototype/Storybook/local app에서도 가능하지만 승인 기준은 Figma/contract로 돌아온다는 내용 |
| 4 | 디자이너를 위한 개발 협업 용어 번역 | 단독 글 또는 자료형 글 | PR, CI, Storybook, Token, Contract, Source of Truth를 디자이너 언어로 설명 |
| 5 | AI가 다음 세션에서도 이어서 일하게 만드는 handoff 문서 | 단독 글 | agent handoff, CONTEXT freshness, public viewer 검증을 묶으면 좋다 |
| 6 | Exploration, Candidate, Approved를 나누는 이유 | AX 1-3편 보강 | Figma 안의 모든 것을 구현 기준으로 보지 않는다는 안전장치 |
| 7 | 문서가 많아지면 문서 레벨 설계가 필요하다 | Compound 3편 보강 또는 별도 글 | role map, 00-99 번호 체계, Entry/Rules/Playbooks/QA/Archive 구분 |

### Wiki 글감의 핵심 문장 후보

```text
Wiki는 worklog를 예쁘게 정리한 곳이 아니라, 오늘의 시행착오 중 다음에도 반복해서 쓸 기준만 승격하는 곳이었다.
```

```text
AI와 오래 일하려면 결과물보다 '다음 세션이 무엇을 믿고 시작할지'를 설계해야 했다.
```

```text
Figma, Git, Storybook, Worklog가 모두 필요했던 이유는 각자 잘하는 일이 달랐기 때문이다. 문제는 도구가 많은 것이 아니라, 어느 도구가 어떤 판단을 소유하는지 정하지 않는 것이었다.
```

### 당장 추천하는 발행 순서

1. AX 5편 중 4편에 Wiki를 "리서치 승격 레이어"로 짧게 넣는다.
2. 이후 단독 글로 `Wiki는 worklog의 예쁜 버전이 아니다`를 쓴다.
3. Storybook 글은 별도로 빼도 좋다. 디자이너 독자에게 가장 실용적인 글감이다.

## 4. AI 제품 / 운영 실험 글감

상태: 후보 정리

목적: AI 제품을 만들고 운영하면서 생기는 브랜딩, 실험, 데이터, 문서, 자동화 주제를 Medium 글감과 workflow wiki 연구 후보로 나눈다.

읽기 기준: "AI로 이런 것도 할 수 있다"가 아니라, 디자이너가 어떤 기준으로 판단하고 어디에 기록하면 다음 작업이 나아지는지 보여준다.

| 우선순위 | 글감 | 추천 형태 | 메모 |
| --- | --- | --- | --- |
| 1 | AI로 브랜딩 구축 프로세스 | 단독 글 또는 사례 연재 | 생성 결과를 브랜드 기준으로 승격하는 순서. 캐릭터/컬러/말투/모션을 따로 보지 않게 한다 |
| 2 | AI로 캐릭터/모션 생성 프로세스 | 단독 글 또는 case | PrismSpirit처럼 이미지 탐색에서 상태별 모션 QA까지 이어지는 흐름 |
| 3 | 문서 기반 Q&A / 챗봇 | wiki playbook + 글 | worklog, wiki, Notion 아카이브를 챗봇이 읽을 수 있는 source map으로 정리 |
| 4 | 현재 제품 단계 진단 테스트 | 간단 테스트/체크리스트 | PoC, beta, live 단계에 따라 적용할 디자인/데이터/실험 기준 추천 |
| 5 | 문서 의견 넣기 / 댓글 기능 | wiki playbook | comment를 결정 기록, issue, wiki 기준으로 승격하는 흐름 |
| 6 | 디자인 as-is/to-be, A/B 테스트 기준 | 단독 글 또는 template | AI가 만든 여러 시안을 실험 후보로 바꾸는 기준 |
| 7 | UT나 데이터 기반 판단 기준 | 단독 글 또는 guide | 기존 Medium의 "이해/선택/활용" 기준을 UT와 지표로 확장 |
| 8 | PoC와 라이브 제품 유저 데이터 연동 | guide 또는 case | PoC 신호와 라이브 데이터를 같은 기준으로 보지 않기 |
| 9 | 디자인 실험 기록 | template | 실험 가설, 기준, 결과, 다음 액션을 worklog/wiki로 남기는 포맷 |
| 10 | 코드 <-> 피그마 양방향 연동 결과 비고 | case | sync 성공/실패, source of truth, Figma evidence package 기록 |
| 11 | 이미지/텍스트 학습 결과 비교 | case 또는 비교 글 | screenshot, Figma node, token, rule 중 어떤 입력이 더 재현성 있는지 비교 |
| 12 | 기존 Figma 디자인과 시스템을 AI가 반영하게 하는 법 | guide | 승인된 component, token, rule, Storybook evidence를 AI에게 주는 방식 |
| 13 | 모바일로 AI 업무 흐름 제어하기 | 운영 글 또는 playbook | Claude Code 모바일 + Git 연동으로 승인/리뷰/중단 지점만 사람이 잡는 흐름 |
| 14 | AI로 웹사이트 디자인-개발 프로세스 줄이기 | case 또는 비교 글 | Figma Make, Framer, Cursor를 팀 구성과 유지보수 기준으로 비교 |

### 제품/운영 실험 글감의 핵심 문장 후보

```text
AI로 무언가를 만드는 것보다 더 어려웠던 것은, 그 결과를 어떤 기준으로 고르고 어디까지 제품 기준으로 승격할지 정하는 일이었다.
```

```text
PoC에서 맞았던 기준이 라이브 제품에서도 그대로 맞는 것은 아니었다. 제품 단계가 바뀌면 디자인 판단의 기준도 바뀌어야 했다.
```

```text
AI에게 일을 맡기는 운영은 "자동으로 다 하게 만들기"가 아니라, 사람이 개입해야 하는 순간만 선명하게 남기는 일에 가까웠다.
```

### 당장 추천하는 발행 순서

1. 기존 AX 5편을 먼저 VOICE_GUIDE 기준으로 다듬는다.
2. 그다음 `AI로 브랜딩/캐릭터를 제품 톤에 맞추는 과정`을 사례 글로 분리한다.
3. `AI로 웹사이트 디자인-개발 프로세스 줄이기`는 실제 테스트 결론이 있어서 case 글로 바로 전환하기 좋다.
4. `문서 기반 Q&A / 챗봇`과 `제품 단계 진단 테스트`는 wiki 실험 백로그로 먼저 구체화한다.
5. `UT / 데이터 기반 판단`은 기존 Medium 1편의 "이해 가능성, 선택 가능성, 활용 가능성"을 확장하는 후속 글로 둔다.
