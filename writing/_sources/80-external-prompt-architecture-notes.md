# 외부 Prompt Architecture 참고 노트

> 목적: 외부에 공개되었거나 유출 주장으로 공유되는 system prompt 문서를 내부 운영 하네스 개선에 참고할 때의 기준을 정한다.
> 작성일: 2026-06-11

---

## 참고 자료

| 자료 | 성격 | 사용 범위 |
| --- | --- | --- |
| Every `Compound Engineering` | 공개 아티클 | 작업 루프, compound 단계, 운영 철학 참고 |
| `elder-plinius/CL4R1T4S`의 `CLAUDE-FABLE-5.md` | 비공식 GitHub 문서, 유출 주장 자료 | prompt 구조와 섹션 설계만 참고. 사실/정책/source-of-truth로 사용 금지 |

유출 주장 문서는 공식 문서가 아니며, 실제 최신 모델 정책인지 검증할 수 없다. 내부 문서에 원문을 복사하거나 현재 운영 규칙으로 직접 채택하지 않는다.

---

## 하네스 관점에서 참고할 것

외부 system prompt류 문서에서 참고할 가치는 “내용 자체”보다 “구조”에 있다.

| 관찰 포인트 | 내부 하네스 적용 |
| --- | --- |
| 큰 지침을 섹션별로 나눔 | `Entry`, `Rules`, `Playbooks`, `QA`, `Archive`를 분리한다. |
| 해야 할 것과 하지 말아야 할 것을 분리 | 룰 문서에서 positive path와 stop condition을 구분한다. |
| 모호한 요청의 기본 행동을 정의 | `진행해` 같은 넓은 요청은 분석/계획으로 해석하고 write는 승인 후 수행한다. |
| 긴 대화에서 instruction drift를 줄이는 reminder 구조 | `CONTEXT.md` freshness check와 current snapshot을 유지한다. |
| tone/format/tool-use/refusal/safety 같은 범주 분리 | 우리 문서도 한 파일에 모든 것을 넣지 않고 역할별 번호 체계로 분리한다. |
| 외부 정보가 변할 수 있음을 전제 | 최신성이 중요한 내용은 공식 출처 확인 또는 freshness 검증을 둔다. |

---

## 참고하지 않을 것

- 모델 이름, 출시 정보, 정책 내용 같은 사실 정보
- 유출 원문 문장이나 세부 규칙의 복사
- 내부 보안/안전 정책으로 검증 없이 승격
- 지금 운영에 필요 없는 과도한 제약

---

## 내부 규칙으로 승격하는 기준

외부 prompt 구조에서 아이디어를 가져오더라도 바로 `rules`로 넣지 않는다. 아래 과정을 거친다.

1. 외부 자료에서 구조적 패턴만 추출한다.
2. 현재 운영 실패 사례와 연결되는지 확인한다.
3. 이미 있는 문서와 중복되는지 확인한다.
4. 삭제/축약/자동화 중 무엇이 맞는지 판단한다.
5. 실제로 필요하면 `20-29 Rules`, `30-39 Playbooks`, `40-49 QA` 중 알맞은 위치에 반영한다.
6. 반영 뒤 eval/check 또는 수동 regression case를 둔다.

## 하네스 리뷰 질문

3-4주 주기 하네스 리뷰 때 아래 질문을 함께 본다.

- 지금 룰 중 모델 성능 향상 때문에 더 이상 필요 없는 제약은 없는가?
- 예전에는 절차로 막았지만 이제는 자동 평가나 체크로 대체할 수 있는가?
- 한 문서에 너무 많은 역할이 섞여 있지 않은가?
- 외부 참고 자료에서 구조적으로 배울 점은 있지만, 내용까지 따라 하고 있지는 않은가?
- 새로 추가한 룰이 실제 실패 사례를 줄였는가?
