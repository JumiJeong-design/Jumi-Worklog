# 4편. 작업을 잃지 않게 한 운영 설계 — Worklog, Wiki, 문서 레벨, 분업

## 한 줄 요약

기준을 세워도 세션이 길어지거나 끊기면 맥락이 사라진다. **Worklog**는 회고가 아니라 다음 작업을 계산하는 계획 엔진이었고, **Wiki**는 별도의 리서치 레이어였다. **문서 레벨 설계**와 **모바일/데스크톱 분업**은 토큰과 집중도를 아끼는 운영 장치였다.

---

## 운영 설계 1. Worklog Planning

worklog는 단순히 "오늘 한 일"을 적는 기록장이 아니었다. 이번 실험에서는 작은 project management layer처럼 작동했다.

```mermaid
flowchart LR
  A["계획 작성"] --> B["작업 중 체크"]
  B --> C["미완료 / 새 리스크 분리"]
  C --> D["다음 액션 계산"]
  D --> E["반복 교훈은 Wiki로 승격"]
```

이 흐름이 생기자 AI 세션이 끊겨도 이어가기 쉬워졌다. 다음 세션의 AI는 "무엇을 했는지"만 읽는 것이 아니라, "무엇을 하려고 했고, 어디까지 했고, 무엇이 남았는지"를 읽고 시작할 수 있었다.

미완료 항목도 그냥 남기지 않았다. 성격을 나눴다.

- Codex / Claude Code가 이어서 할 일
- 주미님이 직접 확인해야 할 일
- FE / PM에게 확인해야 할 일
- 다음 날짜로 이월할 일
- wiki나 rule로 승격할 후보

이렇게 나누면 AI가 할 수 없는 시각 판단이나 승인 작업을 억지로 완료 처리하지 않는다. 반대로 AI가 할 수 있는 문서화, 검증, 커밋 확인, Storybook 상태 점검은 다음 작업으로 바로 이어진다.

---

## 운영 설계 2. Wiki Research Layer

Wiki는 worklog를 정리한 결과물처럼 보이지만, 실제로는 별도의 리서치 레이어였다.

이번 실험에서는 wiki를 만들기 위해 여러 질문을 조사해야 했다.

- Figma와 Storybook의 역할은 어디까지 다른가?
- Git 문서는 Figma를 대체하는가, 언어화하는가?
- Storybook은 개발자 도구인가, 디자이너 QA 표면이 될 수 있는가?
- FE package와 디자인 시스템 컴포넌트는 어떤 계약으로 연결되는가?
- AI 에디터가 다음 세션에서 바로 읽을 수 있는 문서는 무엇인가?
- worklog의 어떤 내용은 wiki로 승격하고, 어떤 내용은 날짜별 기록에 남겨야 하는가?

이 리서치가 있었기 때문에 wiki 문서가 생겼다.

| Wiki 문서 유형 | 리서치한 질문 |
| --- | --- |
| Figma / Git Sync 경계 | 무엇이 source of truth인가 |
| Component Update Playbook | 컴포넌트 변경은 어디서 시작해야 하는가 |
| Agent Handoff Playbook | 다음 AI 세션이 무엇을 읽고 이어가야 하는가 |
| Daily Worklog to Wiki | 날것의 기록을 언제 팀 지식으로 승격할 것인가 |
| Designer Dev Terms | 디자이너와 FE가 같은 단어로 대화하려면 무엇이 필요한가 |

그래서 wiki는 "정리된 문서"라기보다, 이번 실험에서 얻은 운영 지식을 검증하고 재사용 가능하게 만든 결과물이었다.

```text
worklog = 오늘 실제로 무슨 일이 있었는지
wiki    = 그 일을 겪고 나서 다음에도 쓸 수 있는 운영 지식은 무엇인지
```

## 운영 설계 3. 문서 레벨 설계

기준을 Git에 남기는 것은 필요했다. 하지만 문서가 많아지면 또 다른 문제가 생긴다.

나중에 내가 봐도 어디부터 읽어야 하는지 어려워질 수 있다. AI도 많은 문서를 읽지만, 정작 중요한 현재 기준을 놓칠 수 있다.

그래서 문서도 레벨을 나눠야 한다는 과제가 생겼다.

| 레벨 | 역할 |
| --- | --- |
| Entry 문서 | 새 세션이나 새 작업자가 가장 먼저 읽는 요약 |
| Contract 문서 | 현재 실행 기준. component contract, token contract, agent rules |
| Evidence 문서 | Figma node, 측정값, 과거 조사 근거 |
| Worklog | 날짜별 진행 과정, 시도, 실패, 미완료, 다음 액션 |
| Wiki / Playbook | 반복 가능한 교훈과 운영 패턴 |
| Archive | 현재 기준은 아니지만 보존할 과거 기록 |

문서를 더 많이 만드는 것만으로는 부족했다. 문서를 읽는 순서와 레벨을 설계해야 했다.

## 운영 설계 4. 모바일과 데스크톱 분업

AI 도구는 실행 환경도 달랐다.

Claude는 모바일 앱에서도 바로 사용할 수 있어서, 이동 중이거나 컴퓨터를 켜지 않은 상태에서도 쓸 수 있었다. 짧은 판단, 계획 정리, 회고, 다음 작업 분리, FE에게 물어볼 질문 정리에 적합했다.

Codex는 로컬 repo, 파일 시스템, 빌드, Storybook, 테스트와 연결되어 있기 때문에 컴퓨터가 켜져 있어야 제대로 쓸 수 있었다.

| 환경 | 적합한 일 |
| --- | --- |
| Claude mobile | 생각 정리, 계획, 질문, 회고, 다음 액션 계산 |
| Codex desktop | repo 확인, 문서/코드 수정, 테스트, Storybook 검증, 커밋 전 점검 |

모바일은 작업을 준비하고 이어가기 위한 얇은 레이어이고, 데스크톱은 실제 repo를 만지는 실행 레이어였다.

이 분업을 하면 토큰 소모와 세션 낭비를 줄일 수 있다. 컴퓨터를 켜기 전에 모바일에서 생각을 정리해두고, Codex에서는 정리된 계획을 바탕으로 바로 실행할 수 있다.

---

## 이 편의 결론

기준(3편)이 AI가 움직일 수 있는 경계를 정했다면, 운영 설계는 그 작업이 시간 속에서 흩어지지 않게 붙잡았다.

- Worklog는 오늘의 작업을 다음 액션으로 변환했다.
- Wiki는 반복 가능한 교훈을 팀 지식으로 정제했다.
- 문서 레벨 설계는 많은 문서 속에서 현재 기준을 잃지 않게 했다.
- 모바일/데스크톱 분업은 토큰과 집중도를 아꼈다.

다음 편(5편)에서는 이 모든 장치를 갖추고도 끝까지 사람이 잡아야 했던 것 — **B2C 브랜드 품질의 마지막 디테일** — 과 시리즈 전체의 결론을 정리한다.
