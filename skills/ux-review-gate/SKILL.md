# UX 리뷰 게이트

프론트엔드, public viewer, 문서 뷰어, 모바일 UI, 내비게이션, 편집 화면을 수정할 때는
**구현 전에** 이 게이트를 통과한다.

기준 출처: Avenir-UX의 step-level usability 평가(SEQ, efficiency, clarity, confidence),
Agentic Design Review의 다중 관점 리뷰(배치·계층·색·구성), PrototypeAgent의 의도 정렬/중간 검토 흐름.

## 1. 제안하기 전 — 구조 판단

구현안부터 말하지 않는다. 먼저 아래를 판단한 뒤 **추천안과 버릴 안을 함께** 제시한다.

- 기존 시스템의 중심축과 source of truth
- 정보가 중복될 가능성
- 사용자의 1차 실행 화면
- 새 뷰를 만들 때 생기는 비용

## 2. 이름과 역할

- `햄버거/메뉴`, `홈`, `뒤로`, `목록`, `편집`은 **서로 다른 역할**이다.
  같은 기능에 여러 이름을 붙이지 않고, 다른 기능에 같은 이름을 붙이지 않는다.
- `홈` = 현재 상세/문서 뷰를 닫고 첫 화면으로. `햄버거` = 현재 위치와 무관하게 메뉴/인덱스 열기.
  둘 중 하나로 다른 하나를 대체하지 않는다.
- 버튼 라벨은 사용자의 목적어로 쓴다. 추상어(`인덱스로`)를 쓰기 전에 사용자가 실제로 찾는
  말(`홈`, `메뉴`, `편집`, `문서 열기`)인지 확인한다.

## 3. 모바일 내비게이션

- 메뉴/인덱스는 상시 접근 가능한 drawer 또는 고정 컨트롤로 제공한다.
  메뉴를 다시 열려고 본문 맨 위로 스크롤해야 하는 구조를 만들지 않는다.
- 주요 작업(메뉴 열기, 홈 복귀, 편집, 다음 문서 이동)은 **1탭 이내**로 접근 가능해야 한다.
  스크롤 위치에 의존하는 탐색은 실패로 본다.

## 4. 상태와 계층

- 목록 화면 / 문서 상세 화면 / 편집 링크 상태를 명확히 구분한다.
  상세 화면에서 사용자는 "지금 무엇을 보고 있고 어디로 돌아갈 수 있는지"를 즉시 알아야 한다.
- 상단바, 사이드바/drawer, 본문, 보조 액션이 서로 경쟁하지 않게 한다.
  문서 읽기 화면에서는 본문을 가리지 않고, 탐색은 필요할 때 즉시 열리게 한다.
- 같은 레포의 public viewer는 토큰·spacing·버튼 스타일·markdown 스타일을 공유한다.
  새 UI를 만들기 전에 기존 `viewer.css`/`worklog.html` 패턴을 먼저 본다.

## 5. 검증 — 머릿속 말고 실제 화면

수정 후 최소한 이 경로를 **모바일 기준 실제 화면/DOM으로** 확인한다:

> 홈 진입 → 메뉴 열기 → 문서 열기 → 메뉴 다시 열기 → 홈 복귀 → 편집 링크 확인

## 6. 보고

"무엇을 없앴다"가 아니라 **"사용자가 어떤 경로로 무엇을 할 수 있게 됐는지"**를 적는다.
