# 2026. 6. 22 이후 운영판

이 화면은 날짜별 실행 일정이 아니라, **AI로 디자인 루프를 돌리기 위한 운영판**이다. 지금 필요한 것은 “다음 주에 어떤 컴포넌트를 만들까”가 아니라, AI/Figma 탐색 결과를 누가, 어디서, 어떤 기준으로 판정하고 Git/Storybook으로 승격할지 정하는 일이다.

## 한 줄 결론

**Figma와 AI는 탐색 공간, Git은 개발자 계약, Storybook은 개발자 소비면이자 반복 검증 화면, Worklog는 판단 로그다.**

## LNB 역할

LNB는 긴 내용을 담는 곳이 아니라 이동 장치로만 둔다. `도구/스킬`은 운영 콘텐츠와 같은 1차 위계가 아니라 LNB 하단 보조 유틸리티로 둔다.

| LNB | 역할 |
| --- | --- |
| 기록 | 날짜별 워크로그와 그날의 판단 근거 확인 |
| 운영판 | AI 디자인 루프, 역할 분리, Storybook 정보구조 확인 |
| 백로그 | 아직 일정화하지 않는 결정 대기 항목 확인 |
| 보조 도구 | LNB 하단에서 스킬과 실행 보조 도구 확인 |

## 역할 분리

| 주체 / 접점 | 하는 일 | 보는 곳 | 산출물 |
| --- | --- | --- | --- |
| AI | 대안 생성, 누락 상태 찾기, 정보구조 초안 만들기 | Figma, Worklog, Storybook 초안 | 탐색안, 질문 목록, 상태 매트릭스 |
| 디자이너 | 화면 탐색, Component Set 정리, Variant/상태 판단 | Figma | 승인 후보, 디자인 기준, 예외 케이스 |
| 기획자 | 제품 질문 정의, 유저 플로우 판단, 승격/보류 결정 | Worklog, Storybook Pages/Flows, Figma 탐색안 | 결정 기준, 우선순위, 보류 이유 |
| 개발자 | 실제 계약과 구현 소비 | Git, Storybook | API, props, exports, 상태별 examples |
| Worklog | 왜 그렇게 판단했는지 보관 | 워크로그 | 판단 로그, 다음 질문, 백로그 |

## 기획자 개입 지점

### 1. AI/Figma 탐색 전에 개입

기획자는 “무엇을 만들까”보다 “어떤 질문을 탐색할까”를 먼저 정한다. 예를 들어 `source/trust가 핵심 경험인가`, `vote/chart가 사용자의 결정을 돕는가`, `follow-up question이 추천인가 CTA인가`를 정해야 AI 탐색이 의미를 가진다.

### 2. 페이지와 플로우에서 강하게 개입

기획자는 단일 컴포넌트보다 `Pages`와 `Flows / Prototype`에서 더 많이 개입한다. 질문 입력 → 로딩 → 여러 모델 답변 → 비교/투표 → 후속 질문처럼 사용자의 행동이 이어지는 흐름은 제품 판단 영역이다.

### 3. 승격/보류 판단에 개입

탐색안을 `패키지 컴포넌트`로 올릴지, `페이지 예시`로만 둘지, `백로그`로 남길지는 기획/디자인/개발이 같이 봐야 한다. 기획자는 여기서 제품 필요성, 우선순위, 사용자 흐름의 확정도를 판단한다.

### 4. 완료 기준을 잡는다

개발자에게 넘기기 전 “이게 끝났다고 볼 조건”을 정한다. 예를 들어 source가 없을 때도 답변이 신뢰 가능한지, chart가 실패해도 판단이 가능한지, follow-up을 누르면 어떤 다음 상태로 가야 하는지를 정한다.

## Storybook 정보구조 방향

Storybook은 개발자가 실제로 보는 접점이므로, 컴포넌트와 페이지와 플로우가 섞이면 안 된다.

### Foundations

색, 타이포, spacing, radius, shadow, icon, token 같은 기반 규칙이다. Figma 변수와 Git 토큰이 어긋나면 이 층을 먼저 정리한다.

### Components / Common

Button, Text Field, Checkbox, Radio, Toggle, Badge, Toast, Chip, Spinner, Tooltip처럼 제품 맥락과 무관하게 재사용되는 기본 컴포넌트다. 개발자는 여기서 import 경로, props, 접근성, keyboard/focus, token 사용 기준을 본다.

### Components / Chat

Message Bubble, Answer Card, Chat Input Bar, Model Profile, Bottom Bar, Callout처럼 채팅 표면에서만 의미가 강한 컴포넌트다. 공통 컴포넌트처럼 보여도 데이터 shape, loading/error/fallback, 대화 흐름과 연결되므로 별도 층으로 둔다.

### Components / Layout

Header Nav Bar, Bottom Sheet, Modal/Dialog, Dropdown Menu, Context Menu, Bottom Navigation, Settings Row처럼 화면 골격을 만드는 컴포넌트다. 단일 컴포넌트 story와 페이지 조합 예시를 분리한다.

### Pages

페이지는 컴포넌트 계약이 아니라 조합 결과다. Chat, History, Settings 같은 화면은 “실제 화면에서 조합하면 이렇게 보인다”를 확인하는 곳이다. 개발자 API 문서와 같은 층에 두지 않는다.

### Flows / Prototype

인터랙션 행동이 깊어지면 페이지와도 달라진다. 입력, 선택, 로딩 전환, 실패 fallback, 다음 질문처럼 사용자가 움직이는 흐름은 유저 플로우/프로토타입으로 분리한다.

## 인터랙션 깊이 구분

| 깊이 | 의미 | 주로 보는 사람 |
| --- | --- | --- |
| Level 0 | 단일 컴포넌트 상태 | 개발자, 디자이너 |
| Level 1 | 조합 컴포넌트 상태 | 개발자, 디자이너 |
| Level 2 | 페이지 스냅샷 | 디자이너, 기획자 |
| Level 3 | 인터랙션 시나리오 | 기획자, 디자이너, 개발자 |
| Level 4 | 유저 플로우 / 프로토타입 | 기획자, 디자이너 |

## AI 디자인 루프

1. 기획자가 탐색 질문을 정한다.
2. Figma에서 기존 Component Set과 탐색 프레임을 확인한다.
3. AI에게 대안, 누락 상태, 정보구조 후보를 만들게 한다.
4. 결과를 `Common`, `Chat`, `Layout`, `Page`, `Flow` 중 어디에 속하는지 분류한다.
5. 반복 등장하고 상태가 안정된 것만 Git 패키지 계약 후보로 승격한다.
6. Storybook에 개발자 소비면과 반복 검증 화면을 만든다.
7. 피드백과 보류 이유를 Worklog와 백로그에 남긴다.

## 하네스 운영 원칙

하네스는 규칙을 계속 추가하는 장치가 아니라, 다음 작업이 더 쉬워지도록 실패를 기억하고 낡은 절차를 걷어내는 장치다. 3~4주에 한 번씩 하네스 자체를 검토하고 각 규칙과 문서를 `유지`, `병합`, `제거`, `자동화`로 분류한다.

| 방식 | 역할 |
| --- | --- |
| 에이전트 자기검토 | 작업 결과가 규칙, 계약, 완료 조건을 만족하는지 스스로 점검 |
| 자동 평가 | 필수 규칙, 이전 실패 케이스, 회귀 샘플을 스크립트/체크리스트/평가 도구로 반복 검증 |
| 사람 샘플링 리뷰 | 자동화가 잡기 어려운 디자인 품질, 제품 판단, 문서 과잉 여부를 대표 케이스 중심으로 확인 |

모델 성능이 좋아지면 예전에는 필요했던 제약이 오히려 현재 작업 품질을 떨어뜨릴 수 있다. 유지할 제약과 제거할 제약을 분리하고, 반복 실패는 사람 기억이 아니라 자동 평가나 회귀 케이스로 옮긴다.

## 당장 큰 일감

> 큰 일감의 상세 질문·완료 조건은 🧺 **백로그**를 정본으로 둔다. 운영판에서는 방향만 확인한다.

### Storybook 정보구조 재정리 → 🧺 백로그

`Foundations / Components(Common·Chat·Layout) / Pages / Flows`로 나눌 수 있는지가 핵심 방향. 상세 질문·완료 조건은 백로그의 「Storybook 정보구조 재정리」 카드를 정본으로 본다(중복 관리 방지).

### Figma 관리 구조 감사

Figma의 `Foundation`, `Icons`, `Components`를 기준으로 이미 Component Set인 것과 탐색 프레임인 것을 분리한다. 특히 `UI Components common`, `History`, `Chat`, `UI Layout`, `Reference / Exception`이 Storybook의 어느 층으로 이어질지 본다.

### 판단 로그 정리

오늘 진행하기로 확인된 작업과 보류/백로그를 분리한다. 주미님이 직접 말하지 않은 추상 항목은 오늘 할 일로 올리지 않고, 실제 논의가 생겼을 때 별도 기록한다.

### 하네스 리뷰 루프 만들기

3~4주마다 운영판, 백로그, Worklog, Storybook QA, Prism 계약 문서를 한 번에 훑는다. 이때 새 규칙을 추가하기보다 오래된 제약 제거, 중복 문서 병합, 자동 평가 후보 추출, 회귀 케이스 보강을 우선한다.
