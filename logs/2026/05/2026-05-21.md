### 함정 모음

- **i18n 딕셔너리 아포스트로피** — 단따옴표 문자열 안에 `'`가 포함되면 SyntaxError가 발생하고, 에러 메시지 없이 전체 딕셔너리가 무력화된다. 아포스트로피 포함 문자열은 큰따옴표로 감싼다.
- **TEXTAREA i18n** — `placeholder` 속성이 아니라 `el.textContent`로 바꿔야 실제 내용이 반영된다.
- **JS `style.setProperty()` 우선순위** — `tweaks.js`처럼 인라인 스타일로 CSS 변수를 주입하면 외부 CSS 파일이 무시된다. 테마 CSS는 `html[data-design="apple"]`처럼 스코핑해서 격리한다.
- **Figma 캡처는 첫 화면만** — `flow.html`처럼 JS로 화면을 동적 전환하는 구조는 첫 화면만 캡처된다. 각 화면 개별 URL로 따로 캡처해야 한다.

### 플로우 평가 및 다음 단계

### 오늘 플로우 평가

**잘 된 것**

- 코드 기반으로 디자인 시스템을 구축하는 방향은 맞다.
- CSS Custom Properties를 토큰으로 쓰고, Storybook으로 컴포넌트를 문서화하고, SC/AP 테마 전환으로 디자인 언어를 실험한 것은 탄탄한 기반이다.
- 하루 만에 7개 화면, Storybook, i18n, 테마 전환까지 만든 속도는 강점이다.

**구조적 한계**

- 토큰이 `--accent`, `--bg`처럼 1계층으로 평평하게 설계되어 있다.
- 실제 서비스 수준에서는 Primitive -> Semantic -> Component 3계층이 필요하다.
- `--accent` 하나를 버튼 배경, 링크 색상, 포커스 링 등 여러 곳에서 직접 참조하면 규모가 커질수록 예측하지 못한 곳이 깨진다.

**Figma 연동 방향**

- 코드 -> Figma 스크린샷 방식은 Figma를 문서 도구로 쓰는 것이지 디자인 도구로 쓰는 게 아니다.
- Home 화면 하나만 컴포넌트 인스턴스로 재조립했고, 나머지 6개는 픽셀 캡처본으로 남았다.
- 방향을 정하지 않으면 관리 부담이 쌓인다.

### 디자인 퀄리티를 올리기 위한 추천 프로세스

1. **토큰 계층 정리** — `colors_and_type.css`를 Primitive -> Semantic -> Component 구조로 리팩토링한다.
2. **컴포넌트 접근성** — Button, Composer, Persona Card에 `aria-label`, `role`, 키보드 포커스 스타일을 추가한다.
