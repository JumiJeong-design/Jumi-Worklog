# 2026-07-30

prism 패키지를 npm에 처음 올린 날. 오형남님이 "최신 소스 기준으로 배포 한 번 해달라"고 요청했고, 처음엔 npm 정식 배포 대신 tarball과 깃 브랜치 설치를 안내했다가 김호준님 의견으로 방향이 정리됐다 — 카나리 배포를 버릴 이유가 없고, 빌드 산출물을 깃헙 브랜치(`prism-dist`)에 넣는 방식이 오히려 지속 불가능하다는 것. 릴리즈 파이프라인을 마저 손봐 canary를 먼저 올리고, 이어서 latest `0.2.0`까지 배포했다. 7/14부터 걸려 있던 "배포하지 않는다 — changelog 전용" 방침을 접은 날이다.

## 한 일 — canary → latest 배포

canary 먼저. `canary/sha-version-test` push로 `publish-canary`가 돌아 `@riiid/prism@0.2.0-canary.05a7f381...`이 실제 npm에 올라갔다. Trusted Publishing(OIDC) 경로가 처음으로 끝까지 완주한 시점.

이어서 latest. Version PR #34 `chore: 0.2.0`을 squash 머지(`eeff593`)하니 `publish-latest`가 돌아 `@riiid/prism@0.2.0`이 restricted·`latest` 태그로 배포됐다. 쌓여 있던 changeset 10개가 이번에 전부 소비됐다 — Tooltip 추가, Chat History Panel, ChatInputBar `type="2line"`, ModeToggle, 그리고 피그마 기준 토큰 동기화(neutral·크로마틱 램프 갱신 + purple·pink·cyan 신규).

배포 확인은 워크플로 로그로 한다. 로컬에서 `npm view @riiid/prism`이 404로 나오는데, 이건 미배포가 아니라 restricted 패키지라 미인증 조회가 막힌 것이다.

### 함정

- **에이전트가 배포를 자체 판단으로 취소** — `.changeset/readme.md`의 "배포하지 않는다"(7/14) 문구와 슬랙의 "차주에 npm 올릴게요"를 근거로, 이미 러닝 중인 latest publish 워크플로를 취소했다. 실제로는 개발자와 합의가 끝난 건이었다. 재실행으로 복구했고 남은 영향은 없다. 원인은 stale 문서다 — 방침을 접었으면 그 문구부터 지워야 다음 에이전트가 같은 오판을 안 한다. (해당 문구는 PR #34에 이미 제거돼 있었다)
- **산출물을 깃헙 브랜치로 배포한 오판** — `prism-dist` 브랜치에 빌드 결과물을 커밋해 `git+ssh://...#prism-dist`로 설치하게 한 방식. npm 대신 깃헙을 정적 저장소로 쓰는 셈이라 매번 로컬 빌드를 돌리거나 CI에서 별도 커밋을 만들어야 해 지속 불가능하다. 카나리 배포로 대체. 김호준님이 "에이전트가 깃헙 저장소에 산출물을 넣는 걸 금지하는 문구"를 가드레일로 추가하겠다고 예고.
- **npm unpublish 우려는 이 건에선 과했다** — "레지스트리에 박힌다"가 그 자체로 문제는 아니고, 비공개 패키지라 유출 리스크는 깃헙 저장소를 공개로 바꾸는 것과 같은 선상이다. 공개 패키지를 다시 비공개로 바꾸는 것도 가능하다. 카나리 배포가 semver 호환성 약속을 뜻하지도 않는다.

## 회고

#### AI 도구 활용

- 에이전트에게 배포를 맡길 때 위험한 건 배포 자체가 아니라 **에이전트가 stale 문서를 근거로 사람 결정을 뒤집는 것**이었다. 문서에 방침을 적어두면 에이전트는 그걸 사람의 구두 지시보다 보수적으로 해석한다. 방침을 바꿨으면 문서를 같은 턴에 고쳐야 한다.
- 반대로 되돌릴 수 없는 작업(npm publish)에서 에이전트가 멈춰 서는 것 자체는 설계대로다. 문제는 근거가 낡았다는 것이지 멈춘 것이 아니다.

#### 설계 결정

- 내부 공유 배포 채널은 npm canary로 간다. 깃헙 브랜치 산출물 방식은 폐기.
- latest `0.2.0`을 지금 낸 건 "디자인 픽스 완료"라는 뜻이 아니라 프론트 세팅을 풀어주기 위한 것이다.
