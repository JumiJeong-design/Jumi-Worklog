## Side Panel은 flush다 — zone 536 전제 폐기 (주미님 "A로 하자")

#157 재머지에서 드러난 `layout.md` 두 모델 공존을 read-only 재실측으로 갈랐다. 결론은 **안 A(flush)**.

### 실측이 갈랐다 — 같은 노드, 반대 결론

두 주장 다 제품 파일 `7458:12787`을 인용하고 있었다. `token-contract.md`에도 "2026-08-11 실측 확정 — `7458:12787`에서 패널 520의 zone이 536"으로 박혀 있었다. 오늘 그 노드를 다시 쟀다.

## 전체 비교를 걸었는데 안 돌았다 — 함정이 하나 더 있었다

#161을 머지하기 전에 `workflow_dispatch` 전체 비교를 걸었다. 워크플로는 **success**로 끝났다. 그런데 비교는 안 됐다.

```
ℹ Skipping rebuild of an already fully passed/accepted build
  A build for the same commit as the last build on the branch is considered a rebuild.
  You can override this using the --force-rebuild flag.
Skipping build
```

Chromatic 단계가 **2초** 만에 끝났고(313 스토리 업로드가 될 수 없는 시간), step summary의 Build 번호도 PR 때 만들어진 **668 그대로**였다.

### 두 설정이 물려 있었다

| | 동작 |
|---|---|
| `preview.tsx:9` | 스냅샷을 기본으로 끈다 → **PR 빌드는 스냅샷이 꺼진 채 통과** |
| Chromatic | 같은 커밋에 **이미 통과한 빌드**가 있으면 재빌드를 스킵한다 |

합치면 **PR CI가 초록으로 끝난 커밋에는 전체 비교를 걸 수 없다.** 커밋을 안 바꾸면 몇 번을 돌려도 같다. AGENTS.md가 요구하는 "머지 전 전체 비교"가 정작 필요한 순간에만 동작하지 않는 상태였다.

### 고친 것 — PR #164

- `release.yml` — Chromatic 단계에 `forceRebuild: ${{ github.event_name == 'workflow_dispatch' }}`. dispatch 경로에서만 강제로 다시 찍고 PR·push 경로는 그대로
- `docs/workflows.md` §시각 QA — 두 절 신설. ① PR CI의 `UI Tests` 성공은 시각 근거가 아니다 ② 같은 커밋에 통과한 빌드가 있으면 스킵된다 + **실행 후 Build 번호가 새로 발급됐는지로 확인한다**

⚠️ 이 수정 자체는 **머지 후에만 검증된다.** `workflow_dispatch`는 기본 브랜치의 워크플로 정의로 실행되므로 브랜치에 걸어도 옛 정의가 돈다.

### 오늘 두 번째 정정

"#161 전체 비교 실행 중"이라고 보고했는데 **실행되지 않았다.** 워크플로 success를 실행 근거로 삼은 것이 오독이었다 — 오전의 `UI Tests unchanged` 오독과 같은 모양이다. **초록은 "돌았다"의 근거가 아니다. 산출물(새 Build 번호)이 근거다.**

## Callout — "스토리북에 없지?" 한 줄에서 시작해 계약의 허위 근거까지

주미님 요청:

```

```

없는 게 맞았다. 다만 빠뜨린 게 아니라 2026-08-05 `53fe175`에서 의도적으로 내린 것이었고,
내린 사유("피그마가 계약 대상에서 뺐다")가 사실과 달랐다 — 세트도 action variant도 그대로 살아 있었다.
패키지 코드와 계약 md는 내내 있었고 `ChatPage`가 계속 쓰고 있었으니 **카탈로그 노출만 빠져 있던 상태**다.

### 스토리 복구

`Components/Chat/Callout`으로 되살렸다. 계약의 스토리 요구사항 5종(기본 · tone 매트릭스 · action ·
긴 KR/JA · light/dark)에 `Widths` 1종을 더했다 — 8/13에 정한 폭 계약(컴포넌트가 상한을 갖지 않고
소비처가 정한다)이 스토리에 안 보이면 다음 사람이 또 `max-w-[400px]`를 박는다. 모바일 361 / 웹 800을 나란히 뒀다.

### 색 감사 — 드리프트 3건

세트 5개 variant를 Plugin API로 레이어별 전수 실측했다.

| Variant | 면 | 보더 | 아이콘 | 텍스트 |
|---|---|---|---|---|
| success | `green/50` | `green/700` | `green/700` | `green/800` |
| error | `red/50` | `red/500` | `red/500` | `red/600` |
| info | `blue/50` | `blue/500` | `blue/500` | `blue/700` |
| **Type5** | `blue/50` | `blue/500` | `blue/500` | 제목 `blue/700` · 설명 `neutral/500` |

읽히는 규칙은 둘이었다. **아이콘은 텍스트가 아니라 보더와 같은 shade를 쓴다**(네 톤 예외 없음).
그리고 **`Type5`의 면·보더·아이콘·제목은 `Type=info`와 완전히 같은 변수다** — 별도 형태가 아니라
info 톤 + 액션 레이아웃이었다.

1. **action variant가 중립 면이었다.** 코드는 `surface-muted` + `border-control`에 제목 `text-fg`.
2. **아이콘이 컨테이너 fg를 상속해 한 단계 진했다.** 계약 토큰표에 아이콘 항이 아예 없어서 생긴 누락.
3. **계약이 인용한 피그마 근거가 실재하지 않았다.** "action 표면 = Figma `semantic/surface/base` +
   `semantic/border-default`"라고 적혀 있는데 **두 변수는 그 노드에 바인딩돼 있지 않다.**
   중립 표면은 피그마에서 온 값이 아니었다.

`error` fg의 `red/600`→`red/700`은 드리프트가 아니다 — WCAG AA용 의도된 보정이고 계약에 적혀 있다.

### 사용처를 세니 걱정이 사라졌다

"톤 틴트로 되돌리면 빨간 카드에 검은 버튼이 얹힌다"고 우려를 올렸는데, 주미님이 **"빨간 카드 케이스가
얼마나 생길지 모르겠다"**고 되물었다. 세어 보니 **제품 화면에 0곳**이었다.

실제 액션형 사용처는 SA-1a 잠금 안내 2장뿐이고 **파랑**이다. 그리고 그 톤은 이미 주미님이 정한
결정으로 `plan-26` 「딸려온 결정 — SA-1a Callout 톤」에 근거 3개와 함께 적혀 있었다. `error` + `action`
조합은 피그마에도 제품 화면에도 없고 `ChatPage` 데모와 테스트 1건이 전부였다.

**우려가 존재하지 않는 케이스에 대한 것이었다.** 되돌리면 바뀌는 화면은 SA-1a 하나이고 그건
피그마 실물·기존 결정 둘 다와 맞는다. 반대로 그대로 두면 SA-1a를 코드로 구현할 때 회색 카드가 나온다.

### 반영

`action`이 `inline`과 같은 톤 토큰을 쓰게 했다. 이제 **variant는 레이아웃만 가르고 색은 tone 축이 혼자 정한다.**
아이콘은 전용 토큰을 새로 두지 않고 `callout.{tone}.border`를 재사용했다 — 피그마에서도 보더와 아이콘이
같은 변수라 지금 갈라 둘 근거가 없다. 계약에 「색 계약」 절을 신설하고 허위 근거 인용을 걷어냈다.
회귀 테스트 4건 추가(128 → 132).

### 피그마 세트 2축 분리 (주미님 "개명해야지")

`Type5`는 클론 기본값이 안 지워진 이름이었고, **이 이름이 이미 두 번 사람을 헛짚게 했다** —
`plan-26` 감사에서 한 번, 이 계약에서 한 번(실재하지 않는 변수까지 인용하며). 선택지 3개를 올렸고
주미님이 2축 분리를 택했다.

`Type`{success,error,info,warning} × `Layout`{inline,action}. `Type5` → `Type=info, Layout=action`.
**바꾼 건 이름뿐이고 렌더는 전후 바이트까지 동일하다**(22,235 B). 노드 id와 componentKey도 유지돼

개명 직후 재실측에서 텍스트 오버라이드 3종은 그대로였다 — `plan-26`이 경고한 "variant 바꾸면 override가
날아간다"는 발생하지 않았다.

거스러미 1건: 세트가 5변형인데 조합은 8개라 선택기에서 없는 조합을 고를 수 있다. 제품에 안 쓰이는

## 로그인 에러 표현 — "에러 디자인이 있는데 왜 안 썼지?"에서 시작해 전 구간 컴포넌트화

주미님 질문:

```
여기는 원래 에러디자인이 있는데 안쓴게 어떤항목읹 특정하지 않으려고 한거야?
```

### 답은 "의도가 맞다" — 근거는 파일 안에 이미 있었다

`login / 이메일 로그인 — 실패`가 필드 에러를 안 쓰고 손그림 텍스트를 쓰고 있었다. 캡션(`8125:100163`)에 **"실패 문구는 어느 쪽인지 특정하지 않음(§3.1)"** 이 적혀 있었다 — 계정 존재 비노출이다. 비밀번호 찾기의 "가입 여부 무관 동일 안내"와 같은 계열.

그러니 **문구를 특정 안 한 건 의도**고, 문제는 그 결정이 손그림으로 구현돼 색·크기·귀속이 제각각이었다는 것이다.

### 귀속을 셋으로 갈랐다

| 귀속 | 컴포넌트 |
| --- | --- |
| 특정 입력칸(형식 오류·정책 미충족·중복 이메일) | `Text Field State=error` |
| 인증 코드(불일치·만료·자릿수) | `OTP Input State=error` — **메시지 행 신설** |
| 폼 전체(시도 제한·재전송 제한) | **`Form Error` 신설** |

로그인 실패는 첫째에 해당하되 **두 필드를 모두 error**로 뒀다 — 한쪽만 빨갛게 하면 "어느 쪽인지 특정 안 함" 결정이 시각에서 깨진다.

### 색과 크기 — 대비비가 판단을 뒤집었다

`semantic/text-error`가 `red/500`(#e85044)을 가리켜 **흰 배경 3.71:1로 본문 AA 미달**이었다. DS 필드 에러가 `red/700` 직결이라 "DS가 semantic에서 벗어났다"고 봤는데, 실제로는 **semantic 쪽이 미달**이었고 DS의 테두리 red/500 + 문구 red/700 분리가 옳은 설계였다(테두리는 UI 3:1, 문구는 4.5:1).

주미님 결정으로 **Light alias를 red/600(#cf483e, 4.52:1)** 으로 옮기고 DS 에러 문구 5곳을 primitive 직결에서 풀었다. 다크는 red/500 유지 — red/700의 다크값 `#ffd6d0`은 창백해 에러로 안 읽힌다.

크기는 필드 17 vs 폼 13으로 갈려 있었다. 실측하니 **13은 고른 값이 아니라 흘러든 값**이었다 — 같은 역할 문장이 13과 14로 갈려 있었다. 본문 17·타이틀 16 아래 한 단인 **15**로 통일했다.

### ✕는 원복했다 — 내가 반대로 읽었다

"에러 상태에 지우기 ✕가 없다"를 고치면서 ✕ 디자인까지 물었는데, 주미님 답("x가 크기도 하고 색이 진해서 눈에 띄여서")을 **낮추라는 뜻으로 읽고** 원형 28 → 맨 ✕ 20 `icon-muted`로 바꿨다. 실제로는 **눈에 띄는 게 의도**였다("내가 사이클 해놨는데 왜바꿈?"). 8곳 전량 원복했고, 남긴 변경은 error 4변형에 같은 원형 ✕를 넣은 것 하나다.

### 입력 표면 규칙이 덤으로 나왔다

주미님 지적: "설정에선 회색이 어울리는 것 같은데 기분탓?" — 기분탓이 아니었다. Text Field 35개 중 33개가 흰 면 위 회색 입력인데 설정 비밀번호 변경 2개만 반대였고, 그건 **폼 화면이 목록 규칙(회색 바탕+흰 행)을 입고 있어서**였다. 입력칸이 입력이 아니라 카드로 읽혔다.

- **목록·허브** = 회색 바탕(`surface/base`) + 흰 행(`surface/elevated`)
- **폼** = 흰 바탕 + 회색 입력(`neutral/50`)

### 함정 모음

- **게시 ≠ 수락** — 라이브러리를 게시해도 사용하는 파일은 자동으로 안 바뀐다. 변수는 자동으로 내려오지만(색 27곳) **컴포넌트 구조 변경은 Assets → 라이브러리 → 업데이트 수락**이 따로 필요하다. 주미님이 "뭔 수락?"이라고 물었다 — 자명하지 않은 단계다. 확정 진단은 **키로 import해 인스턴스의 현재 마스터와 대조**: 같은 키인데 사본이 둘이면 수락 대기다
- **옛 세대 마스터 프록시는 수락이 안 먹는다** — OTP 인스턴스 10개는 게시·수락 후에도 옛 구조였다. 키는 같은데 프록시가 옛 세대(`8125:2491`)라 업데이트 대상이 아니었다. Text Field는 최신 프록시라 수락으로 넘어갔다. 해법은 백업 후 `swapComponent`
- **`swapComponent`가 옛 override를 새 노드에 얹는다** — `circle-x`(2벡터) → `lucide:x`(1벡터) 스왑에서 옛 원판 벡터의 stroke `visible:false`가 새 ✕에 얹혀 **색은 맞는데 획이 통째로 안 보였다.** 리턴값은 전부 정상이라 스크린샷으로만 드러났다
- **`resetOverrides()`는 이름과 채움까지 되돌린다** — 원복하려고 불렀더니 노드 이름이 `ClearIcon` → `lucide:circle-x`로 풀려 다음 스크립트가 대상을 **0개**로 셌다. 마스터에 없던 원판 fill·stroke 비표시 override도 같이 날아가 수동 복구
- **집계할 때 조상에 INSTANCE가 있는지 먼저 거른다** — 오늘만 세 번 틀렸다. ①변형별 `findOne('ClearIcon')`이 없는 갈림("box/line이 다르다")을 만들어냈다 ②감사표 수치를 그대로 믿었다 ③`Settings/Row` **인스턴스 안쪽** `row` 프레임 58개를 손복제로 셌다
- **마스터에서 노드를 교체할 때 무엇이 풀리는지** — 표시 on/off·변형·형제 override는 **생존**하고, 교체한 그 노드의 **값(텍스트) override만** 마스터 기본값으로 돌아간다. 웹 9곳 실측
- **리스크는 구조를 읽고 말한다** — "마스터를 갈아끼우면 정상 화면에 에러가 튀어나온다"고 경고했는데 마스터 기본값이 이미 `visible=false`였다. 최악은 "튀어나옴"이 아니라 "켜둔 화면에서 안 보임"이었다. 읽기 전에 말한 대가로 주미님이 한 번 멈췄다("아 아니다 고민이다")
- **AUTO 행간에 160% 스타일을 걸면 줄 높이가 커진다** — 감사표는 "기존 스타일 걸기만 하면 끝"이라 했지만 `Attachment/Sent`·`Lightbox` 6건은 행간이 AUTO라 17→22로 늘었다. 무손실이 아니라 결정 대상이었다
