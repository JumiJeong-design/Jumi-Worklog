### 함정 모음

- **게시 완료와 소비 파일 반영은 다른 사건이다.** DS에서 `getPublishStatusAsync`가 `CURRENT`여도 제품 파일 인스턴스는 새 속성을 못 본다 — 소비 파일 쪽 **라이브러리 업데이트 수락**이 따로 있다. **판정은 세트가 아니라 인스턴스의 `componentProperties`로 한다.** 급하면 `importComponentByKeyAsync`+`swapComponent`로 필요한 인스턴스만 게시본으로 옮긴다(override 생존을 1개로 먼저 시험). **단 미게시 신규 variant는 import 자체가 안 된다** — 이 우회는 게시 이후에만 성립한다. (오후 게시에서는 함께 반영돼 재발하지 않았다.)
- **컴포넌트 세트가 에러 상태면 속성 API가 통째로 실패한다.** `Component set has existing errors`로 조회·축 추가가 다 막힌다. `Text Field`의 원인은 **같은 좌표에 겹친 중복 variant 1개**라 캔버스로는 안 보였다 — variant 이름 목록에서 중복을 세면 잡힌다.
- **문서에 적힌 차단 사유를 액면가로 받지 않는다.** 캡션이 "lucide:eye 추가 후 반영(잔여)"였지만 아이콘은 이미 있었고 진짜 차단은 위 세트 오류였다. **"왜 못 했는지"가 적혀 있으면 그것부터 실측한다.**
- **세션 시작 때 읽은 좌표는 배치 직전에 낡아 있다.** 다크 13장이 다른 페이지로 옮겨졌고 태블릿 행이 `y=6800`→`4546`으로 이동해 있었다. 같은 파일에 다른 세션이 붙어 있으면 **배치 직전 재조회**가 기본값이다.
- **클론한 노드에 `characters`를 쓰면 원본의 strings 바인딩이 조용히 풀린다.** 복제로 화면을 만들면 **바인딩 재연결이 기본 절차**다. `swapComponent` 직후 subtree를 `findOne`으로 훑는 것도 스테일 참조로 터지므로 얕은 `children.find()`를 쓴다.
- **variant를 바꾸면 인스턴스 텍스트 override가 날아간다.** 톤 비교로 Callout을 `warning`으로 돌렸더니 컴포넌트 기본 문구가 나왔다. **비교 목적으로 variant를 만지려면 클론에서 한다.** 방어는 strings 바인딩뿐이다.
- **variant 이름은 페인트의 근거가 아니다.** `Type=Type5`인데 페인트는 `info`와 동일 토큰이었다. 이름만 보고 "override로 칠했다"고 오독했다.
- **라벨만 바꿔 끼우면 색 override가 남는다.** 탈퇴 모달 버튼을 스왑했더니 취소가 빨간 글씨로 나왔다(원래 `탈퇴하기` 슬롯의 `danger` 잔재). **텍스트만 확인하면 성공으로 읽힌다 — 렌더로 본다.**
- **중단된 편집이 파일에는 이미 써져 있을 수 있다.** 중단 후 다시 append해 **폐기본과 채택본이 두 벌로 커밋**됐다(`31e280e` → `b656210`에서 제거). **재작업 전에 파일 현재 상태를 먼저 읽는다.**
- **컴포넌트 세트에 variant를 추가해도 세트 프레임은 자동으로 안 자란다.** `clipsContent`라 세트 높이 밖에 놓인 클론이 **1×1로 렌더**된다(빈 스크린샷). 겹침 검사와 클립 검사는 별개다.
- **`INSTANCE_SWAP` 기본값은 key가 아니라 node ID다.** key를 넘기면 `Property value is incompatible…`로 실패한다(빈 문자열도 거부). 반면 `preferredValues`는 `{type:'COMPONENT', key}`로 key를 받는다 — 한 호출 안에서 식별자 형식이 갈린다.
- **"소비처 0"·"미사용" 같은 이월 메모 자체가 실측 대상이다.** `--layout-overlay-popover`는 `Popover.tsx`가 쓰고 있었다. 믿었으면 공개 토큰을 지우거나 값을 바꿔 브레이킹을 낼 뻔했다.
- **렌더가 멀쩡해도 소스는 깨져 있을 수 있다.** `component.tokens.json`이 8/12부터 유효하지 않은 JSON이었는데 `theme.css`에 정상 생성분이 남아 있어 화면은 멀쩡했다. **생성물이 소스보다 오래 산다** — 빌드 게이트를 안 돌리면 안 보인다.
- **개별 게이트 통과는 `pnpm check` 통과가 아니다.** typecheck·test·build를 따로 돌리고 "전 게이트 통과"라고 보고했다가 CI에서 lint에 걸렸다. **한 명령으로 도는 게이트가 있으면 그걸 돌린다.**
- **클론은 마스터 기본값으로 태어난다 — 그리고 그건 스크린샷에만 보인다.** `setProperties`로 variant를 맞추면 리턴값은 정상인데, 문구·가시성·슬롯은 전부 인스턴스 override라 안 따라온다. 웹 실패 화면이 "버튼 없음"으로 나왔다. **구조 리턴값으로 검증을 끝내지 않는다.**
- **머지 충돌이 없다고 안전한 게 아니다.** 한쪽이 지운 파일을 다른 쪽이 쓰고 있으면 delete/modify가 **충돌 없이 삭제로 자동 해소**된다(`composerGlow.tsx`). 머지 후 삭제 목록을 따로 본다.
- **이름이 같은 원격 세트도 파일마다 노드 ID가 다르다.** 제품 파일의 `8767:89199`로 DS를 조회하면 "세트 없음"이 나온다. DS에서는 `2280:5353`이다 — 인용은 이름이나 key로.
- **오버레이 크기를 프레임 크기로 못 키우는 자리가 있다.** 토스트가 세로 HUG라 닫기 버튼이 1줄 높이를 정하고 있었다. 44로 키우면 48→60, 패딩으로 맞추면 2줄이 64→52. **절대배치(피그마) / 의사요소(코드)로 흐름에서 빼는 게 답이다.**

## 판단 6번 — 어조가 아니라 버튼이 문제였다 (8/13)

"모달 어조 통일"로 올라와 있던 항목인데, 기획서·와프·제품 3자 실측에서 **어조는 이미 규칙적**이고 다른 게 어긋나 있었다.

### 어조 = 되돌릴 수 있는가로 갈린다 (통일 불필요)

| 모달 | 문구 | 되돌리기 | 출처 |
| --- | --- | --- | --- |
| 로그아웃 | `로그아웃하시겠어요?` | 가능 | 화면정의서 SB 원문 |
| 세션 삭제 | `이 대화를 삭제할까요?` | 불가 | 기획서 §4.9 원문 |
| 회원 탈퇴 | `정말 탈퇴하시겠어요?` | 불가·최대 파괴 | 규정 없음 |

와프 로그아웃은 `정말 로그아웃하시겠어요?`로 `정말`이 붙어 있으나 **룰 35상 문구는 기획서가 이긴다** → 화면정의서 원문 유지, 변경 없음.

### 진짜 어긋난 것 — 탈퇴 모달의 버튼 문법

- 세션 삭제 `[취소(outline)] [삭제(solid)]`
- 로그아웃 `[취소(outline)] [로그아웃(solid)]`
- **회원 탈퇴 `[탈퇴하기(outline)] [취소(solid)]`** ← 순서도 강조도 반대

기획서 §4.9(`삭제/취소`)·와프 로그아웃(`[취소] [로그아웃]`)·제품 두 모달이 전부 좌 취소/우 실행인데 **가장 위험한 자리만 반대 문법**이었다. 다른 모달에 익숙해진 손이 오른쪽 solid를 누르면 여기선 취소가 된다. 모바일·웹 2건 정합.

### 딸려온 함정 — 라벨만 바꾸면 색이 남는다

슬롯 구조가 같아 라벨을 바꿔 끼웠더니 **취소가 빨간 글씨로 나왔다.** 원래 `탈퇴하기`가 있던 슬롯이라 `danger`(`2096:26`) 색 override가 남은 것이다. 스크린샷으로 잡아 로그아웃 모달 기준(`728:162`)으로 재바인딩했다. **슬롯 간 라벨 스왑은 색·아이콘 override도 함께 옮겨야 한다** — 텍스트만 보면 성공으로 읽힌다.

### 와프 탈퇴 다이얼로그는 대응 상대가 아니다

와프의 `회원 탈퇴 안내`(+`[인증하기]/[취소]` 세로 스택)는 **본인 인증 앞단**이고 우리 최종 확인 모달과 단계가 다르다(§4.11 = 본인 인증 → 확인 모달 2단계). 이월 목록의 "와프엔 있고 우리엔 없는 4건 ①"이 이것이라 버튼 순서 비교 대상으로 쓰면 안 된다.

## 판단 7번(b) — 소집·도착 숫자: 용어 오류 1건만 (8/13)

"보드가 셋이고 값이 다 다르다"였는데, **일괄 통일을 제안했다가 실측으로 스스로 접었다.**

### 두 층이 있었다

- **전문가** = 에이전트만, 최대 **7**(§2.1·§4.6)
- **AI** = 모델 3 + 에이전트, 최대 **10** — `{k}명의 의견`·참여 AI 목록이 세는 대상(§3.4 `k` = 도착한 **AI** 수)

혼선의 뿌리는 값이 아니라 **용어**였다.

### 고친 것 (2곳)

`Deep - 로딩에서 결과 시나리오`의 `전문가 10명을 소집했어요`·`전문가 10명을 지정했어요` → **7**. 전체 AI 10명을 "전문가"로 부른 캐논 위반이다. 같은 보드의 `AI 10명의 의견을 모으는 중...`·`9명의 의견이 모였어요…`는 **맞는 값이라 두었다**(전체 10 · 헤더는 마지막을 갱신 안 하니 최대 9 — §3.4 그대로).

### 건드리지 않은 것

`추론 규칙` 보드의 `전문가 3명 소집` + `3명 모두 모였어요`는 **프레임 이름이 `펼침 · 5단계 최종 이력 (3명 소집 · 3명 도착)`** 이다. 의도된 3명 시나리오라 통일하면 이름과 어긋난다.

`7명의 AI가 모은`은 구형 `Deep/LoadingCard`(`6533:63495`) — 사고과정 확정 시 통째 교체 대상이라 제외.

### 교훈

**프레임 이름이 의도를 적어 두는 경우가 있다.** 숫자만 세어 "값이 셋이니 통일"로 갔으면 의도된 시나리오 예시를 뭉갤 뻔했다. 오늘만 세 번째다(구분선 28/40 · 데스크톱 32 · 이 건) — **일괄 수정 전에 이름·캡션·컨테이너를 읽는 것이 기본 절차여야 한다.**

## 판단 8번 — Popover 폭·Sheet/Handle 버킷 (8/13)

### (a) Popover 240 → 320 (마스터만)

이월 항목이 "소비처가 0이 됐다"였는데 **틀렸다** — `Popover.tsx`가 기본 폭으로 쓰고 있다. 진짜 상태는 이랬다.

- DS 마스터 `Popover`(`4276:1991`) = **240**
- 토큰 `--layout-overlay-popover` = **240**(15rem)
- **제품에서 이 마스터를 쓰는 유일한 인스턴스 = 320 override**

즉 240은 **아무도 안 쓰는 기본값**이었다. 게다가 `layout.md`가 이미 "첨부는 2026-08-11에 240 → 320으로 올렸다 … 결과적으로 Desktop 팝오버 폭은 `--layout-overlay-menu` 320 한 단으로 모인다"로 결론을 적어 뒀다 — **마스터만 그 결론을 못 따라가고 있던 것**이다.

마스터를 320으로 올렸다(`CHANGED`). **토큰 값은 그대로 뒀다** — 공개 manifest 발행분이라 값 변경이 브레이킹이고, 320은 이미 `--layout-overlay-menu`로 존재해 새 값을 만들 이유도 없다.

### (b) `Sheet/Handle` — 패밀리 유지

8/12에 Sheet 패밀리 6개를 `스토리북 계약 / Chat`으로 옮긴 근거는 "실제 포팅된 SheetShell·SheetProfile·SheetAnswer가 Chat에 있다"였다. 그런데 **`Sheet/Handle`은 단독 포팅물이 없다**(`sheet-family.md` 표에 「단독 컴포넌트로 포팅하지 않았습니다」로 적혀 있다) — 대응 버킷이 비어 "섹션=버킷"으로 자리를 정할 수 없다.

그래도 유지한다. 실질이 `BottomSheet` 핸들 규격의 출처이고(40×4 · `radius/full` · `neutral/150`), 떼면 규격 참조가 흩어진다. 얻는 건 분류 일관성뿐이라 되돌리는 비용이 더 크다. 「다시 열지 말 것 — 옮기려면 규격의 새 출처를 먼저 정해야 한다」로 문서에 박았다.

### 교훈

**"소비처 0"·"미사용" 같은 이월 메모는 그 자체가 실측 대상이다.** 이번에도 메모를 믿었으면 토큰을 지우거나 값을 바꿔 브레이킹을 낼 뻔했다. `grep` 한 번이면 갈린다.

## 로딩 인디케이터 규칙(룰 39) 신설 + 히스토리 상태 3종 정리 (8/13 오후)

시작은 주미님 질문 하나였다 — "로딩 디자인을 다 똑같이 스피너 쓰는 게 맞나?"
전수해 보니 문제는 "다 똑같아서"가 아니라 **같아야 할 곳과 달라야 할 곳을 가르는 규칙이 없어서**였다.

### 룰 39 — 아는 것이 많은 쪽부터 고른다

4단계 사다리를 `design-system/rules.md` 39번으로 세웠다. 콘텐츠 대체 > 결정형 진행 > 스켈레톤 > 스피너.
자리별 취향이 아니라 **그 대기에 대해 무엇을 아는가**로 고르고, 위에서부터 성립하는 걸 쓴다.
스피너가 맨 아래인 건 취향이 아니라, 인디케이터 중 유일하게 아무 정보도 주지 않기 때문이다(남은 시간·결과 모양·진행률 전부 없음).

현행 6곳 전수 판정 = 맞음 3(전부 20px 슬롯이라 정당한 폴백) / 틀림 3(목록 로딩·`AttachmentChip`·`Button`의 `...`).
룰 35(Deep 진행바 폐지)를 이 규칙으로 되살리지 못하게 차단 문구도 같이 박았다 — 그쪽은 인디케이터 판단이 아니라 와프 기준 캐논 판단이다.

### Empty State 세트 3층화

감사에서 소비처 7개가 **전부 `no-chat`** 하나였다. `no-results`·`error`는 소비처 0. 실패 화면조차 `no-chat`에 텍스트를 덮어쓰고
RetryButton을 화면 프레임에 절대좌표로 얹은 상태였고, 로딩 화면은 설명 줄을 끈 것으로 흉내내고 있었다. 셋 다 한 컴포넌트였다.

- `action` 불리언 신설(기본 false) — 제목/설명 아래 Button(outline/m) 슬롯. **빈 상태만 2층이고 실패는 3층이라 빈 상태만 허전해 보이던** 구조적 원인.
- `media` 불리언 신설(기본 false) — `no-chat`의 일러스트 슬롯 180×131. 8/10에 뺐던 걸 되살리되 상시 노출이 아니다.
- 실패 화면(`8104:99382`)을 `Type=error` + `action=true`로 전환, 떠 있던 RetryButton 숨김.

`RetryButton` 재사용은 안 했다 — 계약이 "답변 생성 실패 + 남은 횟수 1/3, 180×40 고정"이라 상한이 없는 목록 로드와 의미가 안 맞는다.
버튼에 새로고침 아이콘을 되살릴지는 주미님 "굳이 ..?"로 **텍스트만으로 종결**. 내 추천 근거가 "원래 있던 요소"라는 관성뿐이었고,
빼는 쪽 근거(라벨이 이미 `다시 시도`라 중복 · Action은 범용 슬롯이라 비로그인엔 새로고침이 안 맞음)가 더 나았다.

### 목록 로딩 → 스켈레톤

감사에서 계획이 뒤집혔다. 원래 "`Skeleton` 세트에 history 행 타입 추가가 선행"이라고 룰 39에 적었는데 두 겹으로 틀렸다.
① 코드 `Skeleton`의 `text-line`은 `h-4 w-full` 바 하나라 폭만 달리해 반복하면 되고 새 타입이 필요 없다.
② 피그마 `Skeleton`은 `layoutMode: NONE`이라 **행 반복을 담을 구조가 아니다.**

**로딩은 범용 스켈레톤의 한 종류가 아니라 그 화면의 상태다.** 축은 소비처에 넣었다 —
`Chat History Panel`에 `type=loading` 신설(행 244×47 · 바 16 · 폭 가변 · 색과 radius는 `Skeleton` 세트에서 승계),
제품 로딩 화면(`8104:99337`)에 적용하고 28px 스피너 걷어냄. 룰 39의 틀린 문구도 정정했다.

### 곁가지 — Skeleton은 왜 안 쓰였나

주미님 질문에 이력을 팠다. 2026-06-26 `feat: Skeleton 컴포넌트 추가 (Base UI)`로 신설 → 2026-08-06 #48 한 커밋에서
자기 스토리·소비 스토리(`DecisionFlow`·`deepReportShared`)가 함께 삭제되며 고아가 됐다.
그때 `DeepCTA.tsx:15`에 "로딩 자리표시는 화면 조립 몫"이라고 방향을 적어놨는데 **그 화면 조립을 아무도 안 했다.**
근본 원인은 순서가 거꾸로였던 것 — "어디서 로딩을 스켈레톤으로 할 것인가"를 정하기 전에 원자부터 만들었다.
그 결정을 오늘 룰 39가 처음 명문화했으니, 오늘 작업이 6/26에 만든 걸 처음 실제 화면에 쓴 셈이다.

### 함정 5건

- **미결로 올린 항목을 승인 묶음에 섞어 실행했다** — "일러스트 슬롯을 없앨지 남길지"를 내가 직접 `### 주미님 확인`으로 올려놓고,
  같은 보고의 실행 2번에 묶어 승인받아 지웠다. 주미님은 세션 첫 메시지부터 "guide 이미지를 넣는다던가"로 반대 방향을 말했었다.
  **내 의견이 주미님 방향과 반대인 자리를 묶음 승인으로 밀었다.** 삭제가 아니라 `visible=false`로 한 게 유일한 방어였다(원복 한 줄).
- **`layoutMode: NONE` 세트에서 `variant.clone()`은 원본 위에 정확히 포개진다** — 절대좌표 세트라 클론이 x/y를 그대로 물고 온다.
  children 순서는 맨 뒤, 이름·개수·크기 리턴값 전부 정상. **세트 스크린샷에서 원본이 사라진 걸로만 드러났다.**
- **새 인스턴스는 마스터 기본값으로 태어난다** — 세트에 같은 부품을 채우는데 기존 둘은 override(회색 면·테두리 없음)고
  새로 만든 셋째는 마스터 기본(흰 면·테두리)이라 한 세트에서 모양이 갈렸다. 자식 이름·개수·크기가 같아 **구조 리턴값으로는 안 잡힌다.**
  대조 기준은 마스터가 아니라 옆 인스턴스의 실제 값이다.
- **마스터 높이 255는 고정 상수가 아니라 플레이스홀더가 만든 값이었다** — 슬롯을 숨기자 164로 줄어 "appendChild가 sizing을 건드렸다"고
  오진하고 `resize`로 되돌리려다 실패했다. 세트가 `GRID`라 행 트랙이 콘텐츠를 hug하고 있었다. 164는 부작용이 아니라 승인된 변경의 직접 결과.

## 판단 9(a) — 토스트·시트 핸들 겹침: 현행 유지 + 복사됨 상태 신설 (8/13)

### 대신 빠져 있던 걸 채웠다 — `Copy` 축

논의 중 **화면정의서 S1·S4가 요구하는 「복사됨 상태」가 컴포넌트에 아예 없다**는 게 나왔다. `Button/ActionBar`에 `Copy = default | copied` 축 신설(3→6 variants · 기본값 현행이라 시각 변화 0).

**표현은 피드백 눌림과 같은 문법**이다 — 아이콘을 바꾸지 않고 버튼 표면이 배경(`913:2`)+테두리(`595:855` r8)를 얻고 아이콘 색이 진해진다(`913:3`→`595:856`).

두 번 잘못 갔다. ①아이콘 스왑(`copy-check`) — 같은 바 안에서 좋아요는 배경·복사는 아이콘이면 **한 줄에 두 문법**이 생긴다(주미님 지적). ②불리언+겹침 사본 — 불리언 하나로 원본·사본을 반대로 못 묶어 **아이콘이 두 개로 보였다**. `Feedback`이 축이면 `Copy`도 축이어야 대칭이다.

이게 겹침 판단도 바꿨다 — **버튼이 1차 확인을 즉시 주므로** 토스트가 3초간 핸들을 가려도 잃는 정보가 없다. 게다가 토스트가 뜬 직후는 방금 복사를 누른 순간이라 시트를 내리려는 시점이 아니다.

### 역할 분리를 명문화했다

한때 "시트 안 복사는 토스트를 빼고 버튼만"을 제안했다가 **폐기**했다(주미님: "버튼도 상태를 표현하고 토스트도 나와야지"). **버튼 = 1차 확인(눌렸다) · 토스트 = 2차 고지(무엇이 됐다)** 로 층이 다르다. 계약에도 "토스트를 대체하지 않는다"로 박았다.

### 함정 2건

- **중단된 편집이 파일에는 이미 써져 있을 수 있다.** 아이콘 스왑 문서화를 도중에 중단했는데 rejected가 아니라 **파일에 반영된 상태**였고, 그 위에 채택본을 다시 append해 **폐기본과 채택본이 두 벌로 커밋**됐다(`31e280e`). 다음 커밋(`b656210`)에서 폐기 절을 걷어냈다. **중단 후 재작업 전에 파일 현재 상태를 먼저 읽는다.**
- **`INSTANCE_SWAP` 기본값은 key가 아니라 node ID다.** `addComponentProperty(name,'INSTANCE_SWAP',<key>)`는 `Property value is incompatible…`로 실패하고 node ID여야 통과한다(빈 문자열도 거부). 반면 `preferredValues`는 `{type:'COMPONENT', key}`로 key를 받는다 — 한 호출 안에서 식별자 형식이 갈린다. 폐기한 경로지만 기록해 둔다.

## 모더레이터 얼굴 위치 결정 + socra 마크 참조 통일 (8/13 저녁)

```
여기서 모더레이터의 위치는 어디로 가야하지? 원래 항상 대화내용 맨 마지막으로 정의했는데
```

`empty data`(`6990:134465`) 화면에서 시작한 질문인데, 답을 찾다가 라이브러리 참조가 갈라져 있는 걸 발견해 그쪽이 본 작업이 됐다. **코드 커밋은 없다 — 전부 피그마 작업이다.**

### 모더레이터의 정체부터 다시 봤다

"대화 맨 마지막"이 아니라 **AI 응답 블록의 푸터**였다. 컴포넌트 이름이 `Answer/Footer`(세트 `3876:2422`)이고 variant가 둘이다 — `Type=mark`(로고만, 로딩 형상)와 `Type=disclaimer`(로고 + 면책 문구). `Chat_추론`은 사고과정 토글 아래에 `mark`, `Chat_답변`은 본문·액션 아래에 `disclaimer`가 붙는다. Chat에서는 응답 블록이 마지막 블록이라 결과가 "맨 아래"와 같았을 뿐이다.

### 카드 위냐 아래냐 → 카드 **안**으로

처음엔 카드 위(사고과정 토글 아래)를 추천했다. 대기 투표 카드는 각주가 "리포트가 완성되면 이 화면은 사라져요"라고 못 박은 임시 표면이라 응답이 아니고, 사라질 표면 아래에 서명을 붙이면 카드 소멸 때 뜨기 때문이다.

```
아 그럼 당신이라면 그 위치에 모더레이터 얼굴을 넣는건?
```

주미님 제안이 더 나았다. 확인해 보니 empty 카드 가운데 아이콘의 마스터가 `lucide:book-open`인데 그 아래 문구가 "질문을 가져오고 있어요!"라 이미 모더레이터 발화였다 — 아이콘만 아무 의미 없이 책을 들고 있었다. 크기도 28×28로 `Answer/Footer`의 마크와 같아 그대로 교체됐다. 화자는 카드 안 얼굴이 맡고, 카드 밖 마크는 대기 구간에서 뺀다.

### A/B 시안 → B 채택

목업 페이지(`8138:108283`)에 4장을 만들어 비교했다. A는 얼굴을 양쪽 카드 모두 좌상단 고정, B는 empty만 센터 유지.

정지 화면은 B가 낫고 A는 카드 하단 180px가 비어 미완성으로 보인다. 결정적이었던 건 **얼굴이 움직이는 횟수**다. B에서도 이동은 대기 진입 → 첫 질문 **1회**뿐이고, 그 뒤 질문1→질문2→다지선다 교체 구간에서는 계속 좌상단에 붙어 있다. 내가 A를 민 이유("카드 교체마다 흔들린다")가 B에서도 성립하지 않았다.

### 진짜 일감은 여기서 나왔다

```
응 저 모더레이터 얼굴은 언제든 바뀔수있다고 가정해야해 사이즈도 커질수있ㄱ
```

이 전제로 확인해 보니 **지금 상태로는 "얼굴 바꾸면 전파된다"가 성립하지 않았다.** 제품 파일의 socra 인스턴스가 마스터 두 갈래로 갈려 있었다 — 116개는 색이 검정 하드코딩인 구세트, 나머지는 눈·입이 변수 바인딩인 현행. 그림은 좌표·path 길이까지 동일하고 **차이는 색 바인딩 유무뿐**이라 육안으로는 구분이 안 된다.

갈림이 인스턴스별로 섞인 게 아니라 **호스트 컴포넌트별로 딱 정렬**돼 있었다(구 참조 116개가 전부 `Answer/Footer` 안). 그건 인스턴스가 옛 스냅샷을 붙들고 있다는 뜻이 아니라 호스트 마스터 자신이 구 세트를 참조한다는 뜻이고, 실제로 라이브러리 업데이트 수락을 눌러도 숫자가 1도 안 변했다.

```
아 어쨌건통일하고 ds에서 관리하는게 낫지않아?
```

DS 파일에서 보니 `Answer/Footer`가 **외부 브랜드 라이브러리의 원격 socra**를 물고 있었고, 같은 파일에 변수 바인딩된 로컬 `socra` 세트(`4048:1726`)가 따로 있었다. 컴포넌트 설명에 "socra 마크는 외부 published 라이브러리 컴포넌트다(remote). 브랜드 확정 시 원본 라이브러리에서 교체한다"고 **의도가 명시**돼 있어 내 판단으로 뒤집지 않고 확인을 받았다. 원격을 직접 물면 내부를 못 고쳐 색을 변수에 못 묶는 게 대가였다.

### 반영한 것

**DS 파일** — `Answer/Footer` 두 variant의 마크를 로컬 socra로 스왑, 내부 레이어명을 `Face`로 통일(`Deep/VoteCard`와 맞춤), 설명을 새 규칙으로 갱신(왜 로컬을 쓰는지 + 브랜드가 바뀌면 로컬 socra만 갈면 된다). 원격 socra 사용처는 이 둘뿐이라 통일은 이걸로 끝났다.

**`Deep/VoteCard`**(`4682:2358`) — 4개 variant 전부 `Context` 행 맨 앞에 얼굴 28×28 삽입. 세트에 속성 둘 추가: `Face`(BOOLEAN, 기본 on)와 `Face swap`(INSTANCE_SWAP, 기본값 로컬 socra). 얼굴 교체는 스왑 속성이, 크기 증가는 오토레이아웃 행이 받는다. 카드 높이 **332→336 / 524→528**.

**제품 파일** — `empty data` 카드의 책 아이콘을 얼굴로 교체(센터 유지). 게시·업데이트 수락 뒤 얼굴 인스턴스 **143개가 단일 현행 세트로 통일, 구세트 참조 0**. 딥 대기 화면 8장에 `Face` 슬롯·속성 반영. 다크에서 마크가 `203,206,210`, 라이트에서 `48,50,59`로 잡혀 모드 전환이 확인됐다 — 통일 전에는 양쪽 다 검정 하드코딩이었다.

> ⚠️ 위 판단 9(b)의 "카드 336 · 초과 50"은 **얼굴 삽입 이후 값**이다. 얼굴 전 카드는 332였으므로 그 초과분에 오늘 늘어난 4px가 포함돼 있다. 되살릴 때 산식을 다시 잡을 것.

### 함정 4건

- **`importComponentByKeyAsync` 실패는 "미게시/삭제" 근거가 아니다** — `Answer/Footer` 키가 "not found"로 튕겨 "라이브러리에서 없어진 스테일 스냅샷"이라고 보고했는데, `search_design_system`으로 조회하니 같은 키가 8/11 갱신 상태로 멀쩡히 살아 있었다. 생존 판정은 `search_design_system`으로 한다.
- **참조 갈림은 호스트 컴포넌트별로 묶어본다** — 호스트별로 정렬되면 마스터 문제, 섞여 있으면 인스턴스 스냅샷 문제다. 이걸 안 가르고 주미님께 라이브러리 업데이트 수락을 시켰다가 116개 그대로인 헛수고를 만들었다.
- **업데이트를 받아도 옛 마스터 프록시는 갱신되지 않는다** — 인스턴스 143개가 전부 새 세트로 넘어간 뒤에도 옛 프록시(`7751:120479`·`7751:120478`)는 계속 옛 세트와 옛 레이어명을 리포트했다. 그걸 보고 "아직 안 됐다"고 한 번 오보했다. **판정은 실제 인스턴스의 `getMainComponentAsync()` 집계로.**
- **INSTANCE_SWAP 기본값은 componentKey가 아니라 노드 id로만 먹힌다** — key를 넣으면 `Property value is incompatible with component property type`이 난다. `preferredValues`의 `type`도 `COMPONENT`/`COMPONENT_SET`만 받고 `LIBRARY`는 거부된다.

### 회고

계약 문서에 적힌 의도를 실측 현상만 보고 뒤집지 않은 건 이번엔 맞게 작동했다. `Answer/Footer` 설명에 "원격을 쓴다"는 이유가 적혀 있어서 스스로 갈아타지 않고 A/B로 정리해 물었고, 주미님이 통일 쪽을 골라 근거가 남았다. 반대로 `importComponentByKeyAsync` 실패를 근거로 "없어졌다"고 단정한 건 도구 하나의 실패를 사실로 승격한 것이라 같은 종류의 실수였다 — 판정 도구를 하나 더 대보기 전에 결론을 말하지 않는다.

### P1 6번 — 토스트 닫기 탭 타깃 32 → 44 (픽셀 변화 0)

plan-10 #16에 "사용처별 겹침 검토 후 보류"로 오래 묶여 있던 항목인데, **걸림돌은 겹침이 아니라
높이 계산**이었다. 토스트는 세로 HUG고 1줄 48 = 8 + **버튼 32** + 8이다. 1줄 높이를 정하는 게
텍스트(24)가 아니라 버튼이라, 버튼만 키우면 60이 되고 패딩을 줄여 맞추면 2줄이 64 → 52로
쪼그라든다(실사용에 둘 다 있다). **답은 흐름에서 빼는 것** — 피그마는 `layoutPositioning=ABSOLUTE`
44×44 + `action=close` variant `paddingRight` 6→38, 코드는 `::before` 44×44.

픽셀 변화 0을 실측 확인했다 — 아이콘 중심 (322, 24)·높이 48·텍스트 칼럼 290이 4 variant 전부 그대로다.
버튼이 원래 fill·stroke 없는 투명 프레임이라 키워도 보이는 게 없다.

"터치 타깃 미달 9건"은 9번 고칠 일이 아니었다. 인스턴스 15개 중 닫기 노출 9개인데 **크기 override가
0건**이라 마스터 1건으로 전부 따라온다.

### 리뷰에서 나온 것 — 스켈레톤 바 16 → 20

주미님: "스켈레톤의 텍스트가 16px여도 높이자체는 26px인데 저렇게 얇게 잡아도되나?"

원래 글자보다 두 배 진해지고 17행이 벽처럼 읽힌다. 사이값 20으로 확정(아이콘 슬롯·`Spinner sm`과
같은 값). 행 47은 패딩 10/10이라 **행 높이는 안 바뀐다.**

`Skeleton` 전역 기본값은 안 건드렸다 — 피그마 변경이 패널 `type=loading`에 한정이라 `text-line`을
