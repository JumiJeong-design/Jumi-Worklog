## ChatPage 다크 색상 정합 + neutral 텍스트 램프 + Figma 역정합

ChatPage 다크가 Figma와 "색이 다르고 이상하다"는 피드백을 Figma read-only 대조로 근본 원인까지 잡았다. 직전 핸드오프의 "사이드바를 완전 flush(색 동일)로" 진단은 **오진**이었고, Figma 실측은 반대(패널이 본문보다 한 단계 밝은 raised 면)였다.

### 코드 정합 (패키지 = 실제 배포물)

- 히스토리 패널 배경 `bg-surface`(#0E0F12) → `bg-surface-raised`(#191A1D, Figma `surface/floating`). 항목 다크 토큰 off-by-one 정정(기본 순흑 #000 → #191A1D).
- **단일 ramp 드리프트 근본 해결:** 코드가 surface용 `gray` 램프 하나로 텍스트까지 칠해 다크에서 Figma `neutral` 텍스트 램프와 어긋났다. mode-aware `color.neutral.{500,700,900}`를 추가하고 텍스트 토큰을 재바인딩 → 본문 #F3F6F9·히스토리 #DADEE2·보조 #A0A3A7 등 Figma 정확값.
- 웹 chat 하단 본문 하드컷 → 모바일과 동일 scrim 페이드로 입력창 뒤로 자연스럽게 사라지게 함.
- 검증: `token:build`/`typecheck`/`test`(43) 통과, Playwright 픽셀 대조로 Figma 다크와 일치 확인.

### 인사이트 (드리프트 패턴)

- Figma는 텍스트용 `neutral`(모드 flip)과 표면용 surface 스케일이 분리돼 있는데, 코드 포팅 때 `gray` 하나로 합쳐서 라이트에선 안 보이다가 다크에서 갈라졌다. 다크 정합은 "단일 ramp로 두 스케일을 표현하려는 시도"를 깨야 풀린다.
- 채팅 내부 요소를 컴포넌트별로 대조하니 **Figma 쪽이 코드보다 덜 일관**했다(아바타 배경·모델명·카드 배경이 컴포넌트마다 제각각, 카드가 다크에서 순검정으로 떨어짐). 이런 경우 코드를 기준으로 두고 Figma를 맞추는 역방향 정합이 옳다.

## 이후 계획 재정렬

기획이 아직 미정인 상태이므로 6/23 이후 날짜별 컴포넌트 구현 일정은 확정 계획에서 내리고, 후보 백로그로 남긴다. 이후 계획은 "무엇을 만들지"보다 "기획·디자인·프론트 루프가 반복 가능하게 유지되는지"를 기준으로 운영한다.

### 중요한 일감

- **하네스 관점** — Storybook을 결과물 갤러리가 아니라 Theme / Viewport / Locale / Long Content / Empty / Error / Fallback 상태를 반복 확인하는 검증 장치로 유지한다. `token:build`, `typecheck`, `test`, `storybook:build`, Chromatic 시각 QA의 실행 기준과 소유자를 작업 단위마다 분리한다.
- **운영 루프 관점** — 프론트 적용, 디자인 탐색, 기획 탐색이 서로 다른 속도로 움직이는 것을 인정하고 각 루프의 입력과 산출물을 분리한다.
- **프론트 루프** — FE에게 컴포넌트 구현 지시가 아니라 data shape, interaction wiring, responsive/fallback 조건, source/chart 실패 상태 질문을 전달한다.
- **디자인 탐색 루프** — Figma source-of-truth가 확정된 것과 탐색 중인 것을 분리한다. read-only 감사, 변경안, 영향 범위, rollback, 승인 후 반영 순서를 유지한다.
- **기획 탐색 루프** — POC 변경, 사용자 시나리오, multi-agent 비교 방식, source/trust 표현, chart 판단 구조를 결정 로그로 남긴다.
- **백로그 관점** — `CollapsibleAnswer`, `CollapsibleUserMessage`, `Citation`, `SourceCard`, `SourceSection`, `ChartContainer`, `MetricCard`, `ScoreBar`, `ComparisonBarChart`, `MultiAgentComparison`은 날짜 확정 일감이 아니라 후보 백로그로 보관한다.
- **문서/워크로그 관점** — worklog는 plan / log / roadmap / skills 운영 인덱스로 유지하고, 긴 결정사항은 wiki 또는 notes로 분리한다. 이후 plan은 체크리스트보다 미결정 / 결정 / 이월 상태가 드러나게 작성한다.
- **리스크 관점** — 기획 확정 전에 props, variant, component namespace를 고정하지 않는다. 범용 surface와 slot 구조를 우선하고, 구체 컴포넌트 계약은 Figma / POC / FE 적용성이 맞물릴 때 당겨온다.

### Storybook 정보구조 / 개발자 소비면 보강

- 개발자가 실제로 보는 접점은 Figma 전체가 아니라 Git 패키지와 Storybook이다.
- Storybook은 단순 전시장이 아니라 개발자 소비면이자 디자이너 반복 검증 화면이다.
- Storybook 정리는 `Foundations`, `Components / Common`, `Components / Chat`, `Components / Layout`, `Pages`, `Flows / Prototype`처럼 층을 나눠서 본다.
- 컴포넌트 안에서도 기본 컴포넌트와 채팅 전용 컴포넌트를 분리한다.
- 페이지는 컴포넌트 계약이 아니라 조합 결과로 보고, 인터랙션 행동이 깊어지면 유저 플로우/프로토타입으로 분리한다.
- AI 디자인 루프는 탐색안을 바로 계약화하지 않고, Figma 탐색 → 분류 → 반복 검증 화면 → Git 계약 후보 → Worklog 판단 로그 순서로 돌린다.

### LNB / 운영판 / 백로그 재정리

- LNB는 긴 내용을 담는 영역이 아니라 `기록`, `운영판`, `백로그`, `도구`로 이동만 돕는 얇은 장치로 둔다.
- `운영판`은 AI 디자인 루프, Storybook 정보구조, 기획자/디자이너/개발자 접점을 보는 본문 문서다.
- `백로그`는 날짜가 확정되지 않은 컴포넌트 후보가 아니라 결정 대기 질문을 모아두는 본문 문서다.
- 기획자는 AI/Figma 탐색 전 질문 정의, Pages/Flows 검토, 승격/보류 판단, 완료 기준 설정 지점에 개입한다.
- Storybook은 개발자 소비면이므로 `Foundations`, `Components / Common`, `Components / Chat`, `Components / Layout`, `Pages`, `Flows / Prototype`가 섞이지 않게 정리해야 한다.
