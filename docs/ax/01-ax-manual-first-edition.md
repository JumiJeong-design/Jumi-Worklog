# 01. AX 워크플로 매뉴얼 1차 — 흩어진 넷을 한 벌로 묶기

상태: ✅ 1차 완료 · 기간: 2026-09-08 (하루, 저녁부터 자정 넘어서까지)

## 문제 정의 / 도입 배경

AX 정리를 하겠다고 노션에 목록을 하나 적어 두고 있었다. 「AX 정리 주제」 다섯(스토리북에서 개별 컴포넌트 코드를 안 쓰던 이유 · 발행이 빠져 몇 번을 돌려도 같은 결과가 안 나오던 구조 · rule 문서를 안 읽던 이유 · 모션 정합 · 토큰 절약)과, 에이전트에게 반복해서 보내던 요청 문구(DS 검토 · 화면↔DS 왕복 · DS→스토리북 · 배포 · 병렬 · 맥락 복구 · 마무리).

그런데 이 목록이 공유용인지 개인 정리용인지가 흐렸고, 같은 내용이 네 군데에 흩어져 있었다.

- 요청 문구 개정본 — 노션 「에이전트 지침 2609」
- 에이전트 지시문 두 벌과 사람용 짝 문서 — 워크로그 저장소 `docs/21~24`
- 이렇게 된 이야기 — 연재 「AX 실험 5편」(6월)
- 실험 기록 형식 — ax-log 스킬

가지가 여러 갈래로 뻗어서 정신이 없다는 게 솔직한 출발점이었다. 그리고 이게 곧 Socra 디자인 제품 매뉴얼이 될 것 같다는 감각도 있었다. 목표를 「AX 공유이자 매뉴얼이자 어떤 디자이너에게도 통용되는 기준」 한 벌로 잡았다.

## 작업 과정

### 1단계. 정본을 어디에 둘지 (저녁)

에이전트는 처음에 「워크로그 저장소에 안내문 한 장으로 넷을 잇자」고 했다. 나는 그게 아니라 회사 노션에 DB를 하나 파서 하나씩 아카이빙하는 쪽이었다.

```
여기에 하나씩 아카이빙 해보면 어떨까
```

```
여기에 저장하는게 정본이야
```

정본이 노션 DB「AX-Product design」(소크라 AI 프로덕트 디자인 아래)으로 정해졌다. 레포 문서는 여기서 내려가는 사본이다. 에이전트가 「연재를 잘라 넣으면 6월 상태 매뉴얼이 된다」고 했는데, 연재를 자르는 게 아니라 새로 쓰는 문서라고 잡았다. 연재는 6/11~27 실험 2주치라 게시 게이트 · 훅 · 워크트리 격리 · 색인표가 0건이다.

### 2단계. 장 구조 (밤)

에이전트가 「매뉴얼이면 운영(요청 문구)부터」라고 했고, 나는 구축부터 가야 한다고 했다.

```
ax workflow 구축부터가야하는거 아닌가
```

```
하네스는 운영이지
```

```
그치 구축과 운영 운영에서도 UX,브랜딩, ai, 프론트, 기획 다 나뉘어지는거 알지
```

구분이 넷으로 정리됐다. 지도 · 구축(전제 · 채널 다섯과 게시 게이트 · 시각 기준 · 행동 기준) · 운영(하네스 + 영역별 문구) · 원리. 원리는 나중에 내가 「단점도 적고, AI가 잘하는 것과 사람이 판단할 것도 갈라 적고, 의사결정자들 사이에서 중간안을 찾은 것도 적으면 좋겠다」고 하면서 생겼다. 장이 아니라 판단이라 구분을 하나 더 뒀다.

첫 레코드는 장 본문이 아니라 지도 한 장이었다. 열한 장을 지금 다 쓰면 정리하다가 또 가지가 뻗는다.

### 3단계. 장 본문 (자정 전후)

「이어서 해」를 세 번 했다. 원리 1 → 3 → 2 → 구축 0·1 → 구축 2·3 → 운영 0. 에이전트가 「문구 여섯은 원문을 옮기는 일이라 다음 세션」이라고 접으려 했는데 「너가 할 일 다했어?」를 듣고 마저 올렸다. 열다섯 장.

장 꼴은 같다. 무엇을 세우나(돌리나·시키나) · 왜 이 자리가 필요한가(사건 한두 줄) · 만든 뒤 확인할 것. 원리 장만 다르다. 주장 한 줄 · 근거 사건 · 따라 하는 사람이 미리 정해 둘 것. 문구 장은 언제 쓰나 · 이렇게 시킨다(코드 블록) · 왜 이 문장인가 · 결과를 이렇게 확인한다.

### 같은 세션에서 같이 간 것 — 프로젝트 정리

중간에 「이건 다른 에이전트가 하던 프로젝트 정리 재료랑 겹친다」는 걸 알았다. 에이전트는 갈라 두자고 했는데 결이 비슷해서 한 세션에서 같이 가기로 했다. 주어만 다르다. 프로젝트 정리는 「내가 이렇게 판단했다」, 매뉴얼은 「이럴 때는 이렇게 한다」. 같은 사실(예: 「기준이 이미 있는 일을 위임한다」)이 튜터 케이스 「결」과 매뉴얼 원리 2에 각각 들어갔다.

## 트러블슈팅

다섯 주제는 매뉴얼 장 안에 들어갔다. 여기서는 어느 장에 어떻게 들어갔는지와, 이 세션 자체에서 난 문제 하나를 적는다.

**문제 1**: 스토리북에서 화면을 조합할 때 개별 컴포넌트 코드를 안 썼다
- 원인: 스토리북이 「디자이너가 다 운영하는 곳」으로 잡히면 FE 영토 문제가 되고, 「검수 표면」으로 잡히면 패키지 컴포넌트를 그대로 써야 한다. 초기엔 전자에 가까웠다.
- 해결: 6/2 미팅에서 「우선 검수 기준으로만」으로 들고 갔다. 스토리북은 Figma를 대체하지 않고, 제품에 올라가는 중간 뷰다. → 구축 1 「스토리북의 장점」, 원리 3 사례 1.

**문제 2**: 발행이 빠져서 몇 번을 돌려도 같은 결과가 안 나왔다
- 원인: 디자인 시스템 파일에서 고친 것이 게시되지 않으면 제품 파일은 옛 값을 본다. 변수는 자동 전파, 컴포넌트 구조는 수락 필요. 게시와 수락을 가르는 규칙(43번)이 있었는데 다른 규칙의 하위 항목에 묻혀 열흘간 같은 오판이 났다.
- 해결: 루프 그림에 「게시」를 따로 그렸다. 게시 여부는 상태값이 아니라 제품 파일 인스턴스로 잰다. → 구축 1 「게시 게이트」.

**문제 3**: rule 문서를 안 읽었다
- 원인: 51개 879줄은 통독이 안 되고, 검색은 찾을 단어를 이미 알 때만 걸린다. 문제를 「새 레이아웃 설계」로 잡으면 「컴포넌트 재사용」 규칙을 찾을 이유가 없다.
- 해결: 「이럴 때 이 번호를 연다」 색인표를 지시문에 뒀다. 규칙이 두 번 안 지켜지면 훅으로 옮긴다. → 구축 3, 운영 0, 원리 1 단점 1.

**문제 4**: 모션을 어디서 고치고 git과 어떻게 정합하나
- 원인: 피그마는 정지 컷만 있어서 모션 선택지를 못 고른다. 정지 컷으로 내린 첫 판단 셋이 셋 다 틀렸다.
- 해결: 모션 정본은 스토리북. 값은 스토리 컨트롤로 넘기고 확정되면 상수로 올린다. 후보는 한 화면에 나란히. → 문구 6 「그 밖에」, 원리 2 사람 몫 1.

**문제 5**: 토큰이 어디서 새는지 몰랐다
- 원인: 재기 전엔 모른다. 재 보니 셸 출력이 3할이었다.
- 해결: 그 뒤에 압축 도구(Headroom)를 붙였다. 감으로 줄이지 말고 먼저 어디서 새는지 잰다. → 원리 1 단점 5, 운영 0.

**문제 6 (이 세션에서 난 것)**: 노션에 쓴 한글이 옆 글자로 깨졌다
- 원인: 에이전트가 툴 호출 JSON에 한글을 `\uXXXX` 이스케이프로 적었다. 한글 음절은 코드포인트가 빈틈없이 이어져 있어서 한 자리 틀려도 에러가 안 나고 멀쩡한 옆 글자가 된다. 「컬러→컴러」「몫→몷」「잰다→재다」「곧→곱」「띠→띄」「뭔지→뽔지」. 열다섯 장에서 서른 자리 넘게 났다. 앞선 일곱 번이 멀쩡했다고 안전한 게 아니었다.
- 해결: 쓸 때마다 fetch로 되읽어 대조했다. 고치는 코드포인트를 손으로 셌더니 셋이 또 틀려서(쵰·댈·뭔) `python3 -c "print(hex(ord(c)))"`로 뽑아 맞췄다. 규칙(리터럴로 쓸 것)은 CLAUDE.md에 이미 있었는데 안 지켜졌다. 되읽기가 없었으면 회사 노션에 그대로 남았다.

## 결론 / 한계

> 🚨 문체가 아직 에이전트 것이다. 사실은 맞고 목소리는 아니다. 10~11월에 내 말로 바꾼다.

> 🚨 운영 문구는 프론트와 공통만 차 있다. UX · 브랜딩 · AI · 기획은 빈칸이다. 그 영역에서 같은 요청을 두 번 타이핑하게 될 때 채운다.

> 🚨 원리 1 「단점」이 있는 매뉴얼이라 도입을 설득할 때 쓸 수 있지만, 단점을 적은 만큼 「그래도 왜 하나」가 원리 2·3에 충분히 실렸는지는 다시 읽어야 한다.

> 💬 구축과 운영을 가르는 기준이 「하네스는 운영이다」 한마디로 정리됐다. 구축은 구조, 운영은 매일 돌리는 것. 이 구분이 없었으면 훅과 워크트리가 구축 편에 들어가 매뉴얼이 셋업 문서처럼 읽혔을 것이다.
