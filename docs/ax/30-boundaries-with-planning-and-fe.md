# 30. 기획·프론트와 경계를 나눈 자리

상태: ✅ 완료 · 기간: 2026-07-27 ~ 2026-09-07

## 문제 정의 / 도입 배경

에이전트는 눈에 보이는 어긋남을 전부 고치려 든다. 그런데 어긋남 중에는 **고칠 권한이 나에게 없는 것**과 **애초에 어긋남이 아닌 것**이 섞여 있다.

기획서에 없는 화면을 찾으면 「확인 필요」에 올리고, 화면 문구와 변수 값이 다르면 결함으로 세고, 개발자에게 알릴 게 생기면 슬랙 메시지를 쓴다. 셋 다 방향이 틀렸다. 어느 것이 누구 몫인지 선을 그어 두지 않으면, 에이전트가 남의 일을 만들어 낸다.

## 작업 과정

### 1. 기획서 원문은 절대 안 건드린다

정본은 PM이 관리하는 노션이고 레포 파일은 그 사본이다. 디자이너나 에이전트가 손대면 원본과 어긋난다.

「기획서에 넣어 드릴까요?」라고 물었다가 **「기획서 원문은 절대 건들지 말고」**를 받았다. 제안이 있어도 직접 쓰지 않고, 반영 여부는 주미님이 PM에게 넘길지 판단한다.

**디자인 결정이 기획서와 달라지면 피그마 화면 가이드에 표기만 남긴다.** 「원안은 이랬는데 이렇게 바꿨다, PM 확인 필요」 형태다. 문서 수정 제안은 하지 않는다.

### 2. 「기획서에 없다」는 결함이 아니다

정본에 규정이 없다는 사실만으로 확인 항목이 되지 않는다. 주미님 표현으로 **「기획에 없는 내용도 있는 거지 뭐」**다.

기획서는 정책과 흐름을 정하고, 화면 단위 디테일은 디자인이 채운다. 이 프로젝트에도 사례가 여럿이다. 다크 모드 토글, 탈퇴 완료 화면을 두지 않기로 한 결정, 언어 변경 확인 팝업 문구. 전부 정본에 없는 채로 화면이 먼저 정해졌다.

**갭을 찾으면 표현인지 기능인지부터 가른다.** 표현이나 디테일이면 디자인 결정으로 처리하고 근거만 남긴다. 데이터 저장이나 개발 공수가 붙는 기능이면 짧게 적어 두되, 그것도 「넣느냐 마느냐의 결정」이지 오류가 아니다.

대화 이름 바꾸기 컷 두 장을 이 이유로 확인 항목에 올렸다가 「일단 냅둬」로 정리됐다.

### 3. 문구는 기획이 관리한다

하드코딩된 화면 문구를 전부 문구 변수에 묶는 작업을 끝내고 「값이 다른 두 종은 어느 쪽이 정본인가」를 여쭈니, 주미님이 **「스트링 관리는 기획에서 할 거라 피그마는 굳이 신경 안 써도 돼」**로 정하셨다.

문구 변수 컬렉션은 화면 더미와 실제 UI 문구가 섞여 있고, 제품 세 페이지의 미바인딩 8,624노드 중 대부분이 더미다. 로케일 문구의 정본은 기획서와 기획 관리표이지 피그마 변수가 아니다.

그래서 이렇게 정했다. **피그마에서 문구를 새로 묶거나 변수를 신설하거나 값을 고치는 작업을 제안하지 않는다.** 이미 묶인 것은 그대로 둔다. 문구 감사에서 「변수와 값이 다르다」가 나와도 결함으로 세지 않는다.

### 4. 기획에 넘길 때는 요청이 아니라 공유로

JP 문구 137종을 기획 담당자에게 넘길 슬랙 초안을 썼는데 주미님이 다시 쓰라고 하셨다. 내 초안은 「번역 정본이 없습니다 → 정해 주시면 반영하겠습니다 → 이건 어느 쪽이 맞나요?」로, **상대에게 일감을 넘기는 요청서**였다.

주미님이 원한 골자는 이랬다.

> JP 문구가 화면에 시각적으로 문제 없는지 테스트해 보는 과정에서 위 시트를 참고해 토큰화해 봤는데, 화면에는 있는데 시트에는 없는 문구가 몇 개 있어서 임시로 번역해서 테스트 중이다. 혹시 필요하실까 공유드린다.

문구는 기획이 관리하는 영역이라, 디자인 쪽에서 목록을 보내면 그 자체로 「처리해 달라」는 압력이 된다. 실제로 필요한 것은 내 작업을 설명하고 자료를 열어 두는 것이지, 상대의 할 일을 정하는 것이 아니다.

**순서를 이렇게 고정했다.** ① 내가 뭘 하다가 ② 뭐가 나왔고 ③ 그래서 임시로 어떻게 해 뒀다 ④ 필요하시면 쓰세요. 판단을 구하는 질문은 이 톤에서 빼고, 정말 필요하면 나중에 따로 여쭙는다.

### 5. 개발자에게 알릴 것은 메시지가 아니라 패키지 문서에

글래스 배치 주의사항 셋을 슬랙 메시지로 세 번 다듬고 있었더니 주미님이 말씀하셨다. **「어차피 개발자들은 이 패키지를 받아서 쓸 건데, 기록해서 받아 쓰는 사람한테 알려 주면 되는 거 아니냐」**

맞는 지적이었다. **한 번 보내고 마는 메시지는 다음에 들어오는 개발자가 못 본다.** 그때까지 그 내용은 컴포넌트 주석과 계약 문서에만 있어서 코드를 여는 사람만 볼 수 있었다.

소비 앱이 보는 자리는 패키지 README다. 계약 문서에는 그 절을 가리키는 한 줄만 넣어 양쪽에서 걸리게 한다.

## 트러블슈팅

**문제**: 문서를 고쳤는데 개발자에게 안 갔다

- 원인: 문서 변경에 체인지셋을 안 붙였다. 붙이지 않으면 npm으로 안 나가고 git에만 남는다.
- 해결: 문서 변경에도 patch 체인지셋을 붙인다.

**문제**: 예제를 복사했는데 아무 일도 안 일어난다

- 원인: 받는 쪽 선언이 필요한 API인데 한쪽만 적었다. 앵커 이름을 쓰려면 앵커 요소도 그 이름을 선언해야 한다.
- 해결: **예제는 반쪽으로 쓰지 않는다.** 양쪽을 다 적는다.

**문제**: 문서에 적었는데도 남은 일이 있었다

- 원인: 「앞으로 이렇게 쓰세요」는 문서가 하지만, **「지금 이미 잘못돼 있는지」는 문서가 못 잡는다.**
- 해결: 그건 사람에게 한 번 물어봐야 한다. 물어볼 말은 한 줄로 줄여서 전달한다.

## 결과

- 기획서 원문 불가침이 규칙으로 굳었다. 차이는 피그마 가이드 표기로만 남긴다.
- 「기획서에 없음」을 사유로 남의 판단을 요구하지 않게 됐다.
- 문구 감사에서 나오는 불일치를 결함으로 세지 않게 됐다.
- 다른 직군에 넘기는 메시지의 순서가 정해졌다.
- 개발자 주의사항이 패키지 README로 옮겨졌다.

## AI가 잘한 것 / 디자이너가 보정한 것

- AI: 문구 미바인딩 8,624노드처럼 규모를 정확히 잰 것. 계약과 README 양쪽에 걸리게 배치를 설계한 것.
- 디자이너: 다섯 자리 전부에서 방향을 잡아 준 것. 특히 「받아 쓰는 사람에게 알려 주면 되지 않냐」는 지적은 전달 방식 자체를 바꿨다. 요청서를 공유문으로 다시 쓰게 한 것도 같은 결이다.

## 아쉬운 점 · 리스크

- 기획서와 다른 결정이 피그마 주석에만 있다. 그 조항만 읽는 사람은 코드가 낡은 줄 안다.
- 문구를 안 건드리기로 하면서, 화면과 시트가 갈린 상태가 그대로 남는다. 정본이 기획 쪽에 서기 전까지는 감사로 못 닫는다.
