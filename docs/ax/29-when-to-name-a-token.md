# 29. 토큰을 언제 만들고 언제 안 만드나

상태: ✅ 완료 · 기간: 2026-06-23 ~ 2026-09-08

## 문제 정의 / 도입 배경

디자인 시스템 일을 에이전트에게 시키면 토큰을 잘 만든다. 너무 잘 만든다. 「하드코딩된 값이 있으니 토큰으로 묶겠습니다」가 기본 반응이고, 그대로 두면 이름만 늘어난다.

치수 토큰을 전수로 바인딩하고 굵기 토큰을 일곱 개까지 늘렸을 때 주미님이 물었다. **「걍 이름 줘야 하나? 숫자로 할까 걍 ㅡㅡ」** 정당한 질문이었다. 여백 541곳을 `size/N`에 묶어서 얻은 게 「아무 숫자나 못 쓰게 막는다」 정도였다.

그래서 선을 그었다. 토큰을 만드는 기준과, 애초에 새로 만들 일이 아닌 경우를 가르는 기준 둘 다 필요했다.

## 목표

- [x] 이름을 반드시 줄 것과 숫자로 둘 것을 가른다
- [x] 「신설」과 「포팅 누락」을 가르는 절차를 만든다
- [x] 토큰 축으로는 안 잡히는 사각지대를 잰다
- [ ] 색 semantic 재바인딩 (별도 계획으로 분리, 미착수)

## 사용한 툴

- Claude Code · Figma MCP 전수 스캔 · 렌더 픽셀 측정

## 작업 과정

### 1. 이름을 주는 기준 셋, 안 주는 기준 셋

**반드시 이름을 주는 것.**

- **색.** 다크 모드에서 깨진다. 숫자로 박으면 글씨가 사라진다.
- **뜻이 값과 다른 것.** 완전히 둥근 모서리는 9999든 999든 뜻이 「완전히 둥글게」다. 값이 이름을 대신하지 못한다.
- **나중에 따로 움직일 것.** 강조용과 글래스용은 지금 값이 같아도 갈라 둬야 한 쪽만 굵힐 수 있다.

**숫자로 둬도 되는 것.**

- **이름이 곧 값인 것.** `size/12`는 12를 12라고 부르는 것뿐이다.
- **쓰임이 두세 곳뿐이고 따로 움직일 일이 없는 것.**
- **브랜드 로고와 아트웍.**

묶기 전에 묻는 문장 하나로 정리했다. **「이게 나중에 혼자 움직일 일이 있나」.** 없으면 숫자로 두고 넘어간다.

여기 딸린 규칙이 하나 더 있다. **이름과 실제가 어긋나면 이름 쪽을 고친다.** `stroke/width/control`이 1.8인데 정작 컨트롤은 1.5를 쓰고 있어서 값을 1.5로 내려 맞췄다. 이름만 보고 묶으면 어긋남이 그대로 굳는다.

### 2. 새로 만들 일인지 옮길 일인지 먼저 가른다

코드에 없는 토큰을 보고 「신설할까 말까」로 판단을 열었다가 지적을 받았다. 코드에는 선 색이 하나뿐인데 피그마에는 이미 두 개가 정의돼 있었다. 패키지가 그중 하나만 옮기면서 둘을 하나로 합쳐 버린 것이었다.

**피그마가 1차 기준이니, 피그마에 이미 있는 것은 설계 대상이 아니라 동기화 대상이다.** 이걸 신설 문제로 말하면 두 가지가 나빠진다. 이미 끝난 디자인 결정을 다시 여는 셈이고, 비용을 과대평가해서 「안 해도 된다」는 잘못된 결론으로 샌다.

같은 날 차트 색에서도 같은 일이 있었다. 차트 색이 제각각이라 새 이름 공간을 만들자고 했는데, 주미님이 거부하고 「이미 있는 파운데이션 쓰라」고 하셨다. 원인이 토큰 부재가 아니라 **브랜드 램프에서 매번 다른 순서로 골라 쓴 것**이었기 때문이다. 해법은 새 토큰이 아니라 기존 램프를 고정 순서로 쓰는 사용 규칙이었다.

**새 토큰을 제안하기 전에 「기존 토큰의 조합이나 순서 규칙으로 해결되나」를 먼저 묻는다.**

### 3. 만든 토큰을 실제로 쓰는지는 별개다

전수 스캔에서 나온 결과가 이렇다. 계약 컴포넌트 70개 중 **52개**가 색을 semantic이 아니라 원시 램프에 직접 걸고 있었다. 토큰 층은 있는데 채택률이 낮았다.

역할이 같은데 토큰이 제각각인 자리가 여럿이었다.

- 흰 표면에 `neutral/white` 85곳 대 `semantic/surface/Floating` 20곳. **`neutral/white`는 다크에서 검정이라 카드가 통째로 뒤집힌다.**
- 본문 텍스트에 `neutral/900` 54곳, `neutral/black` 43곳이 섞여 있고 `semantic/text-primary`는 12곳뿐이었다.
- 반전 텍스트와 에러 계열은 semantic 토큰이 있는데 **사용처가 0곳**이었다.

그래서 채택률 문제를 컴포넌트 통합보다 앞에 뒀다. 다만 자동 일괄 치환은 금지했다. 툴팁 반전 · 컨트롤 켜짐 · 스켈레톤 · 상태색은 토큰 신설이 먼저라 판단이 필요하다.

### 4. 토큰 축 감사가 통째로 못 보는 자리가 있다

크기 토큰은 **크기만** 갖고 굵기가 없다. 굵기는 컴포넌트의 Tailwind 클래스에 직접 박혀 있어서, **계약 문서와 토큰 JSON을 맞대는 축으로는 절대 안 걸린다.** 줄 높이·자간·말줄임도 같은 사각지대다.

하루에 두 번 걸렸다. 한 라벨은 마스터와 계약이 둘 다 15px Medium인데 코드만 SemiBold였고, 토큰 축 감사를 다 돌리고도 못 잡았다. 크기를 고치러 그 줄을 열다가 눈으로 봤다. 이어서 연 클래스 축에서는 계약 문서 쪽이 낡은 경우도 나왔다.

## 트러블슈팅

**문제**: 굵기 클래스를 정규식으로 세니 0건이 나왔다

- 원인: `className`이 여러 줄 `clsx(...)` 블록이라 크기와 굵기가 다른 줄에 있다. **한 줄 정규식으로는 못 센다.** 굵기 클래스 98곳 중 같은 줄에서 크기까지 읽힌 것이 69곳뿐이었다.
- 해결: 중괄호와 따옴표를 균형 잡아 블록을 통째로 묶었다. 80블록이 잡혔다. 첫 결과 0건은 「없다」가 아니라 「안 봤다」였다.

**문제**: 문서에서 굵기를 훑으니 엉뚱한 것이 걸렸다

- 원인: `600`을 낱말째로 잡으면 `neutral/600`과 노드 좌표가 걸린다.
- 해결: `SemiBold` 낱말과 「굵기 600」 꼴만 남겼다. 그래도 오탐 둘이 남는다. 같은 줄의 작은 스타일을 가리키는 경우와, 「22px SemiBold에서 24px Medium으로 올렸다」 같은 **이력 문장**이다.

**문제**: 변수 API로 값을 대조했더니 다크 값을 잘못 보고했다

- 원인: 변수 API 단독을 믿었다.
- 해결: **실제 렌더 픽셀 측정이 근거다.** 값을 대조할 때는 렌더까지 한 번 본다.

## 결과

- 토큰 명명 기준이 `design-system/rules.md` 3번에 올라갔다. 이름을 주는 셋, 숫자로 두는 셋이다.
- 「포팅 누락인가 신설인가」를 먼저 가르는 절차가 생겼다.
- 굵기 클래스 축 감사가 별도 계획으로 열렸다. 아직 안 잰 축은 줄 높이와 자간이다.
- 굵기 기준을 정했다. 20px 이상 제목은 Medium, 18px 이하는 SemiBold를 유지한다. 18px에서 Medium으로 내리면 본문과 굵기가 같아져 위계가 크기 3px에만 걸린다.

## AI가 잘한 것 / 디자이너가 보정한 것

- AI: 전수 스캔으로 채택률과 역할별 불일치를 숫자로 낸 것. 굵기가 토큰 축에 안 걸린다는 사각지대를 찾고 클래스 블록 파싱으로 실제로 센 것.
- 디자이너: 「걍 숫자로 할까」로 토큰 증식을 멈춘 것. 차트 색에서 새 이름 공간을 거부하고 기존 램프의 사용 규칙으로 방향을 바꾼 것. 「피그마에 이미 있으면 옮기는 일이다」라는 프레이밍을 잡아 준 것.

## 아쉬운 점 · 리스크

- 색 semantic 재바인딩은 스캔만 하고 미착수다. 스캔값이 두 달 넘게 지났으니 착수 전에 다시 재야 한다.
- 상태색 semantic이 에러만 있고 성공·정보·경고가 없다. 이건 진짜로 신설이 필요한 자리다.
- 줄 높이와 자간은 아직 안 쟀다.

## 한 줄 평

토큰을 만드는 기준은 「값이 반복되나」가 아니라 「나중에 혼자 움직이나」다. 그리고 새로 만들기 전에, 이미 어딘가에 있는 건 아닌지 먼저 본다.
