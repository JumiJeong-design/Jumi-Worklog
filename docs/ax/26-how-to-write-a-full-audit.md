# 26. 전수 감사를 어떻게 짜는가

상태: ✅ 완료 · 기간: 2026-08-05 ~ 2026-09-08

## 문제 정의 / 도입 배경

「이 토큰을 쓰는 자리가 몇 곳이냐」는 물음에 답하려면 파일을 전수로 세야 한다. 그런데 이 수치가 계속 틀렸다. 그것도 한 방향으로만 틀린 게 아니라 양쪽으로 틀렸다.

- 실제로는 있는데 0개로 나온다.
- 실제로는 없는데 1,348개로 나온다.
- 같은 대상을 두 번 셌더니 280과 388이 나온다.

수치가 틀리면 그 위에 얹은 판단이 전부 틀린다. 없는 일감 1,348개가 생기거나, 있는 일감을 「깨끗하다」로 넘긴다. 그래서 감사 스크립트를 짜는 방법 자체를 규칙으로 만들었다.

## 작업 과정

### 함정 1. 숨은 자식이 통째로 빠진다

플러그인 API에는 「보이지 않는 인스턴스 자식을 건너뛴다」는 전역 플래그가 있다. 이게 켜져 있으면 `children` · `findAll` · `findOne`에서 전부 빠진다.

이걸 몰라서 「라이브러리 업데이트가 인스턴스에 안 내려왔다」로 진단하고 **주미님께 업데이트 수락까지 요청했다. 애초에 필요 없는 일이었다.** 컴포넌트 교체로도 안 바뀌어서 「통째로 갈아야 한다」까지 갔다.

**더 나쁜 경우는 경고가 안 뜨는 것이다.** 어떤 대상을 세니 280이 나왔는데, 며칠 전 다른 방법으로 센 값이 388이었다. 280도 그 자체로는 이상할 게 없어서 0이나 빈 배열처럼 튀지 않는다. 앞선 값이 없었으면 그냥 넘어갔다.

그래서 **전수 집계는 플래그를 스크립트 첫 줄에 적고, 그 값을 수치 옆에 같이 남긴다.** 같은 대상을 두 번 세서 수가 다르면 먼저 의심할 것은 파일 상태가 아니라 플래그다.

복제 직후에도 똑같이 난다. 로그인 화면 다섯 장을 복제해 제목과 버튼을 고치는 스크립트에서 플래그를 안 적었더니 복제본 안 텍스트가 통째로 안 잡혀 교체가 전부 빠졌다. 프레임 직속 텍스트 삭제는 정상으로 되어서 더 헷갈렸다.

### 함정 2. 기획 보드가 화면으로 잡힌다

제품 파일에는 화면만 있는 게 아니라 기획서 보드가 같이 있다. 토큰에 안 묶인 채우기를 셌더니 1,427건 중 1,348건이 이 보드들이었다. 이걸 「화면이 토큰을 안 쓴다」로 읽으면 없는 일감이 1,348개 생긴다. 실제 디자인 화면의 미바인딩은 두 페이지 합쳐 27개로 사실상 깨끗했다.

판별 기준을 폭으로 잡았다. 화면은 모바일 393이나 웹 1440이고, 폭이 2,000을 넘으면 문서 보드다. 375×812는 기획서 쪽 규격이다.

**다만 폭만으로 거르면 안 된다.** 섹션은 보드가 아니라서, 섹션 자체의 폭으로 거르면 그 안에 든 화면이 통째로 사라진다. 조상 중 프레임만 보고 판정하고, **걸러낸 수를 보고에 같이 적는다.**

### 함정 3. 컴포넌트 이름으로 세면 양쪽으로 틀린다

색 뱃지 컴포넌트 인스턴스를 세니 활성 페이지에서 0개였다. 거기서 멈췄으면 「정본 화면은 이 색을 안 쓴다」로 결론 낼 뻔했다. 같은 범위를 변수 바인딩으로 다시 재니 **활성 페이지가 그 램프를 558곳에서 물고 있었다.** 뱃지가 아닌 다른 요소들이 같은 색을 직접 걸어 쓰고 있었다.

반대 방향도 있다. 이름으로 대상을 세면 안 그려지는 노드가 딸려 온다. 진행 막대를 이름으로 훑었더니 89곳이 더 나왔는데, 열어 보니 전부 20×20 타원이었고 그 슬롯이 꺼져 있었다. 형태도 다르고 화면에 안 그려지니 값을 옮겨도 바뀌는 게 없다.

가시성은 노드 자신이 아니라 조상을 올라가며 본다. 대상 노드는 보이는 상태였고 부모 슬롯이 꺼져 있었다.

```js
function drawn(n) {
  let q = n;
  while (q && q.type !== 'PAGE') { if (q.visible === false) return false; q = q.parent; }
  return true;
}
```

이름으로 셀 때 하나 더 있다. 개명된 인스턴스는 빠진다. 같은 대상이 이름으로는 48곳, 마스터 참조로는 115곳이었다.

### 함정 4. 저장 키 이름이 문서와 다르다

선 두께를 변수에 걸면 `boundVariables.strokeWeight`에 안 들어간다. **네 변 키로 쪼개져 저장된다.** 190건을 걸어 놓고 다시 재니 11건만 잡혀서 「바인딩이 되돌아갔나」로 읽을 뻔했다.

```js
const SIDES = ['strokeTopWeight','strokeBottomWeight','strokeLeftWeight','strokeRightWeight'];
const isBound = !!bv.strokeWeight || SIDES.some(s => bv[s]);
```

REST API는 또 다른 이름을 쓴다. 모서리 반경이 플러그인에서는 `topLeftRadius` 계열인데 REST에서는 중첩 객체 안의 다른 이름이다. 플러그인 이름으로만 훑어서 반경 31,694건과 선 두께 8,770건을 통째로 놓쳤다. 그 결과 **반경 사용률이 0.0%로 나왔는데 실제로는 91.7%였다.**

컬렉션 이름으로 찾는 것도 같은 함정이다. 「간격 컬렉션이 없으니 패딩과 간격은 숫자로 남는다」고 문서에 적었는데 오판이었다. 간격 변수는 크기 컬렉션 안에 있었다. **컬렉션이 아니라 스코프로 판정한다.**

### 함정 5. 값만 보면 아무것도 안 그리는 노드가 딸려 온다

선 두께가 1.5인 노드를 세니 335건이었는데, 그중 선 페인트가 실제로 있는 건 얼마 없었다. 나머지는 선 배열이 비어서 화면에 아무것도 안 그린다. 이걸 모르고 「1.5 미바인딩 9건」이라고 계획 문서에 올렸고, 조건을 다시 재니 **1.5는 0건**이었다.

```js
const hasStroke = Array.isArray(n.strokes) && n.strokes.length > 0;
const isBound   = !!bv.strokeWeight || SIDES.some(s => bv[s]);
const hasOwner  = /* 조상에 COMPONENT_SET이 있는가 */;
// 대상 = hasStroke && !isBound && hasOwner
```

여기서 나온 교훈이 하나 더 있다. 계획 문서에 「1.5가 두 토큰 사이라 값만으로는 못 정한다」가 대기 사유로 적혀 있었다. 컬렉션 설명으로는 맞는 말인데, **실제로 그 갈림길에 서는 자리는 0건이었다.** 2.0도 마찬가지로 미바인딩 열 건이 전부 로고였다. 「어느 토큰인지 못 정한다」를 대기 사유로 적기 전에 그 값으로 남은 대상이 실제로 있는지부터 센다.

### 함정 6. 대표 자리 하나만 재면 나머지가 깨진 채 통과한다

토스트 폭을 353으로 맞췄는데 한 자리에서 313이 됐다. 그 자리만 뷰포트가 콘텐츠 크기에 맞춰지면서 좌우 마진이 두 겹으로 걸렸다. 같은 화면에 353짜리와 나란히 놓여 40px 어긋났다.

**측정 스크립트에 그 노드가 안 들어 있어서 표에는 353만 찍혔다.** 표가 통과했으니 됐다고 볼 뻔했고, 컷을 눈으로 보고 잡았다.

그래서 고치기 전에 그 컴포넌트가 놓이는 자리를 먼저 열거한다. 측정은 대표 노드 하나가 아니라 전부 훑고 부모의 폭과 패딩까지 찍는다. 수치 표가 통과해도 컷을 몇 장 본다.

### 함정 7. 인스턴스 집계 도구가 과소 집계한다

메타데이터 조회로 센 인스턴스 수는 인스턴스 내부를 안 펼친다. 1,095로 나왔는데 플러그인 API로 다시 세니 2,823이었다. 인스턴스 빈도 감사는 반드시 플러그인 API로 센다.

이 파일에서는 인스턴스의 37%가 고아 마스터를 참조하고 있었다. 디자인 시스템 파일 복제본에서 갈라져 나온 흔적이다. 라이브러리를 고쳐도 이 인스턴스들에는 안 내려간다.

고아를 셀 때 주의할 점이 있다. 인스턴스에서 마스터로 거슬러 세면 **실제로 쓰이는 variant만 잡히고 안 쓰이는 것은 목록에서 빠진다.** 마스터의 부모가 컴포넌트 세트면 그 세트를 대상으로 올려 잡는다. 처음에 하나로 셌는데 실제로는 세트 전체(변형 넷)가 고아였다.

## 트러블슈팅

**문제**: 고아 마스터를 지울 수가 없다

- 원인: `remove()`를 부르면 성공하고 `removed`도 참으로 바뀌는데, 끝나고 보면 노드가 다시 부모 없는 고아로 돌아와 있다. `remove()`가 하는 일은 트리에서 떼어내는 것까지이고 노드를 파괴하지 않는다.
- 해결: 플러그인 API로는 파일에서 못 없앤다. 할 수 있는 건 참조를 0으로 끊는 것까지다. 그러면 어느 화면에도 안 닿으니 실무적으로는 거기가 끝이다.
- 덧붙임: **페이지를 통째로 지워도 안 없어진다.** 폐기 페이지 넷을 처분해 파일이 열한 페이지에서 일곱으로 줄었는데 고아 넷이 그대로 남았다. 고아는 애초에 페이지에 속해 있지 않아서 페이지와 함께 지워질 것이 없다.

**문제**: 선 두께를 문자열에 붙이니 스크립트가 터졌다

- 원인: 네 변이 다르면 값이 `figma.mixed` 심볼이다.
- 해결: 타입을 먼저 본다. `??` 체인으로 읽으면 0인 변이 먼저 잡혀서 아래쪽만 2인 밑줄형을 통째로 놓친다. 실제로 두 곳을 첫 스캔에서 놓쳤다.

**문제**: 기록에 남은 수치를 그대로 인용했다

- 원인: 워크로그에 적힌 소비처 수를 근거로 썼는데, 그 수치가 다른 조건으로 센 것이었다.
- 해결: 수치를 인용할 때는 어떤 조건으로 셌는지 같이 확인한다. 조건이 안 적혀 있으면 다시 센다.

## 결과

- 감사 스크립트의 함정 일곱이 규칙 문서 44번 계열로 정리됐다. 44-5-1(고치기 전 전 페이지로 센다) · 44-5-2(0은 검산할 대상이 없다) · 44-6-1(섹션은 보드가 아니다)이 여기서 나왔다.
- 반경 사용률 수치가 0.0%에서 91.7%로 바로잡혔다.
- 고아 마스터 복구 방법이 정해졌다. 섹션에 다시 붙이면 참조 링크가 유지되고 소비처 값은 안 바뀐다(51건 실측).

## AI가 잘한 것 / 디자이너가 보정한 것

- AI: 전수 스캔을 실제로 돌린 것. 같은 대상을 두 방법으로 세서 차이를 찾아낸 것. 판정 조건을 코드로 적어 다음에 재사용 가능하게 만든 것.
- 디자이너: 「지금 보는 건 기획서야」 한마디로 1,348건이 허수임을 가른 것. 수치가 이상하면 화면을 직접 열어 확인한 것.

## 아쉬운 점 · 리스크

- 함정이 일곱인데 앞으로도 늘어날 것 같다. 감사 스크립트를 짤 때마다 이 목록을 훑는 습관이 필요하다.
- 고아 마스터는 참조만 끊고 파일에 남아 있다. 다음에 세는 사람이 또 잡을 수 있다.

## 한 줄 평

전수 감사에서 위험한 수치는 「이상해 보이는 수」가 아니라 「그럴듯해 보이는 수」다. 0과 1,348 둘 다 검산 대상이다.
