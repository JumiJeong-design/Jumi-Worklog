# 24. 같은 컴포넌트를 화면 크기마다 다르게 쓰기

상태: ✅ 완료 · 기간: 2026-06-29 ~ 2026-09-07

## 문제 정의 / 도입 배경

Socra는 웹 우선이고 모바일 웹도 같이 간다. 한 컴포넌트가 393에서도 1440에서도 서야 한다. 여기서 반복해서 걸린 질문이 「무엇이 늘어나고 무엇이 고정인가」였다.

처음에는 이걸 매번 따로 판단했다. 그러다 보니 값이 화면마다 흩어지고, 어떤 값은 **왜 그 숫자인지 아무도 모르는 채로 굳었다.** 드로어 폭 337이 그랬다. 「337 고정」과 「화면 폭 − 56」이 대표 폭 393에서 완전히 같은 값이라, 어느 쪽인지 정해진 적이 없는데도 정해진 것처럼 굴러갔다.

## 목표

- [x] 화면 크기별로 늘어나는 것과 고정인 것을 가른다
- [x] 값이 아니라 산식으로 적는다
- [x] 접힌 사이드바 접근 방식을 정한다
- [x] 실제로 쓰이는 크기를 전수로 센다
- [ ] Mode Toggle 후보 확정

## 사용한 툴

- Claude Code · Figma MCP 전수 실측 · 스토리북 뷰포트 프리셋 · CDP 렌더 대조

## 작업 과정

### 1. 데스크탑에서 늘어나는 것과 고정인 것

「데스크탑에서 이전 질문을 볼 방법이 뭐냐」는 물음에서 시작했고, 답은 「모바일과 똑같은 흐름, 크기만 가변」이었다. 그러면 무엇이 가변인지를 정해야 한다.

컬럼은 800으로 고정하고 가운데 둔다. 그 위에서 이렇게 갈렸다.

- **컬럼을 따라 늘어나는 것**: 사고 과정 토글(768) · 입력바 · 헤더 페이드 밴드
- **고정**: 캡슐 400 · 카드 520 · 리포트 560 · 스크롤 FAB 44

캡슐만 모바일 361에서 데스크탑 400으로 늘렸다. 이유가 값에 붙어 있다. 361을 그대로 두면 소진 상태 문구가 한 줄에 안 들어간다(자연폭 252 + 32 + 8 + 80 = 372). 마스터에 개행이 있는 건 393 폭 사정이고, 데스크탑에서는 한 줄이 맞다.

태블릿 1024 컷은 만들었다가 지웠다. 없어도 되는 자리였다.

### 2. 값 대신 산식으로 적기

모바일 히스토리 드로어 폭을 다시 봤다. 393에서 337이면 옆에 홈 화면이 56만큼 남는다. 이 56이 핵심이다. 진입 화면이 옆에 서 있다는 신호이자, 탭해서 닫는 어포던스다.

그런데 다른 폭에서 어떻게 되는지가 안 정해져 있었다.

- 360에서 337을 고정하면 슬리버가 23이 된다. 홈 햄버거 아이콘 24px 중 5px만 남고, 터치 영역 44×44 규칙에 미달한다.
- 430에서 337을 고정하면 슬리버가 93이라 헤드라인이 문장 중간에서 끊긴다.

**「화면 폭 − 56」으로 정했다.** 337은 393에서 나온 결과값이지 원인이 아니다. 근거 셋이 같은 방향이었다. ① 푸시 방식을 고른 근거가 슬리버 자체라 그 폭이 흔들리면 결정이 깨진다 ② 337 고정은 360에서 규칙 위반이다 ③ 레이아웃 문서가 이미 「모바일 가로 치수를 숫자로 적는 것 자체가 틀렸다, 화면 폭에서 빼서 얻는다」를 원칙으로 세워 뒀다.

시각 변화는 0이다. 393 컷 열한 장에서 값이 그대로다. 그런데도 고친 이유는, **다른 폭 컷을 만들 때 337을 그대로 옮기면 안 된다는 것이 컷에 안 적혀 있었기** 때문이다.

### 3. 접힌 사이드바는 클릭 토글로 편다

접힌 레일에서 최근 채팅에 어떻게 닿을지를 정했다. 후보는 셋이었다. 레일에 상시 노출 · hover로 살짝 미리보기 · 클릭해서 펼치기.

**클릭 토글이다.** hover 미리보기를 뺀 이유가 여럿이다. 실제로 쓰는 제품이 Gemini 하나뿐이고, 터치에는 hover가 없고, 접근성 기준 1.4.13을 위반하고, 실수로 열리지 않게 하려면 300~500ms 지연이 필요하다. ChatGPT · Claude · Perplexity · Copilot이 전부 「펼침 + 무한 스크롤」이다.

전용 팝오버도 안 만들기로 했다. 검색은 채팅이 쌓인 다음에 붙일 보조 수단이지 유일한 진입점이 아니다.

### 4. 실제로 쓰이는 크기를 센다

버튼 크기 정합 항목이 올라왔다. 「피그마 16 대 코드 15」인데, 이걸 「제품 전체가 바뀐다」로 읽으면 틀린다.

제품 파일 세 페이지에서 버튼 인스턴스 242개를 전수로 셌다. `l`이 159, `s`가 83, **`m`이 0**이다. m은 어느 화면에도 안 나타나서 어느 쪽으로 정해도 화면이 안 바뀐다. 실제로 보이는 두 크기는 이미 일치한다.

**그런데 코드의 기본값이 m이다.** 사용처 121곳 중 104곳이 m으로 잡히는데 대부분 스토리북 데모다. 아무것도 안 적으면 화면에 없는 크기가 나온다.

## 트러블슈팅

**문제**: 구성의 기본값이 결정처럼 굳었다

- 원인: 드로어로 간다고 정할 때 폭만 판단했고 열림 방식은 판단한 적이 없다. 코드의 기존 오버레이 패턴대로 홈을 x0에 깔고 스크림과 드로어를 얹은 상태가 그대로 굳었다.
- 해결: 레퍼런스에서 폭을 가져올 때는 같은 레퍼런스의 열림 방식도 같이 판단하고 기록한다. 이건 지적을 받고서야 드러났다.

**문제**: 이름과 폭만 보고 답변 카드로 오판했다

- 원인: 웹 컷 스물한 개의 래퍼가 393 고정이라 토글이 361이었는데, 그중 다섯 개는 래퍼 이름이 `Answer Card`였다.
- 해결: 열어 보니 26px짜리 빈 프레임이었다. 이름과 폭만 보고 단정하지 않는다.

**문제**: 「지원 폭인지 문서에 없다」고 물었다가 지적받았다

- 원인: 360이 지원 폭인지 확인하려고 물었는데, 스토리북 뷰포트 프리셋에 이미 360×800이 있었고 레이아웃 문서도 이미 360을 계산에 넣고 있었다.
- 해결: 대표 폭이 393 하나라는 것과 360을 안 본다는 것은 다른 이야기다. 묻기 전에 문서를 더 읽는다.

**문제**: 가로 오토레이아웃 안에 배경을 넣으니 플로우에 편입됐다

- 원인: 히스토리 화면 프레임이 전부 가로 오토레이아웃이다.
- 해결: 절대 배치를 명시한다. 그리고 화면 목록은 낡는다. 문서에 열두 장으로 적혀 있는데 그 뒤에 생긴 화면이 혼자 옛 방식으로 남아 있었다.

## 결과

- 데스크탑 확정값이 계약 문서 「데스크탑·태블릿 배치」 절에 들어갔다.
- 드로어 폭이 산식으로 바뀌었다. 계약 문서 · 레이아웃 표 · 스토리북 상수 셋 다 `화면 폭 − 슬리버 폭`이다. 디자인 시스템 가이드라인 보드에도 히스토리 드로어 행을 추가했다.
- 접힌 사이드바 결론이 굳어서 「팝오버로 할까, hover로 할까」를 다시 논의하지 않게 됐다.
- 버튼 m이 화면에 없다는 사실이 기록됐다.

## AI가 잘한 것 / 디자이너가 보정한 것

- AI: 242개 전수로 m이 0곳임을 잰 것. 360과 430에서 슬리버가 각각 23과 93이 된다는 걸 계산해서 산식 결정의 근거를 만든 것. hover 미리보기의 실증과 접근성 기준을 모은 것.
- 디자이너: 「모바일과 똑같은 흐름, 크기만 가변」으로 방향을 한 문장에 담은 것. 오버레이가 아니라 푸시여야 한다고 레퍼런스와의 차이를 짚은 것. 「레퍼런스가 갈릴 땐 원복 말고 판단 기준을 명문화하면 진행해도 된다」는 방침을 준 것.

## 아쉬운 점 · 리스크

- 코드 버튼 기본값이 여전히 m이다. 화면 재현 스토리를 쓸 때 크기를 생략하면 화면에 없는 크기가 나온다.
- Mode Toggle에서 Quick을 감추는 안은 후보 셋을 만들어 두고 미확정이다.
- 디자인 시스템 가이드라인 보드에 드로어 규격 자리가 원래 없었다. 정할 때 올릴 자리가 비어 있다는 뜻이라 다른 규격도 같은 상태일 수 있다.

## 한 줄 평

같은 값이 두 산식에서 나오면, 값이 같은 동안에는 어느 쪽인지 아무도 모른다. 화면 폭이 바뀌는 날 갈린다.
