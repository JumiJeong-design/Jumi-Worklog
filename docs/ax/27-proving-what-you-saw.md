# 27. 눈으로 본 것을 어떻게 증명하나

상태: ✅ 완료 · 기간: 2026-08-19 ~ 2026-09-08

## 문제 정의 / 도입 배경

디자인 판단은 눈에서 시작한다. 「이 화면 비어 보인다」 「이 선이 연하다」 「이 문구 잘린 것 같다」. 그런데 이걸 그대로 보고하면 상대는 확인할 방법이 없고, 나중에 내가 다시 봐도 같은 판단이 나온다는 보장이 없다.

그래서 눈으로 본 것을 수치로 바꾼다. 문제는 **수치로 바꾸는 방식이 틀리면 눈보다 못하다는 것**이다. 실제로 수치가 눈과 반대 결론을 낸 적이 있고, 수치가 맞는데 내가 잘못 본 적도 있다. 둘은 다른 사고라서 가르는 방법이 따로 필요하다.

## 목표

- [x] 「비어 보인다」를 재는 방법을 정한다
- [x] 렌더로 판정할 때의 함정을 모은다
- [x] 측정 스크립트 자체가 틀리는 경우를 가른다
- [x] 규칙과 워크플로 문서에 올린다

## 사용한 툴

- Claude Code · CDP · Playwright · Python PIL · Figma MCP

## 작업 과정

### 1. 「비어 보인다」를 상자 크기로 재면 반대로 나온다

Deep 리포트 도착 화면이 비어 보인다는 판단에서 출발했다. 이걸 요소 상자가 화면을 얼마나 덮는지로 쟀다.

무대 높이를 뷰포트의 34%로 키우니 덮임이 올랐다. 모바일에서 441에서 510으로, 웹 1440에서 388에서 624로. 수치만 보면 개선이다.

**그런데 잉크로 재니 반대였다.** 밝기 225 미만인 픽셀 비율이 3.09%에서 2.66%로 떨어졌다. 상자만 커지고 안은 그대로였기 때문이다.

**덮임은 상자 크기를 재고 그 안이 채워졌는지는 안 본다.** 컨테이너를 키우는 안이 실제로는 더 비었는데 더 좋게 나온다. 「비어 보인다」는 잉크로 재고, 임계는 비율이 아니라 절대값으로 잡는다.

이 방법에도 한계가 있다. 스켈레톤 회색은 잉크가 잘 못 잡는다. 밝아서 임계 위로 올라간다.

### 2. 축소한 렌더를 눈으로 보고 색을 판정하면 안 된다

색 값을 바꾸고 렌더를 받아 확인했다. 그런데 385×3366짜리 노드가 103×900으로 축소돼 왔고, 그걸 눈으로 보고 판정했다가 틀렸다. 축소하면 안티에일리어싱이 색을 밝은 쪽으로 밀어서 옛 값과 새 값이 구분이 안 된다.

**판정은 픽셀 수로 한다.** 최대 크기를 노드 원본 크기로 주고 받은 뒤, 새 값과 옛 값 집합을 만들어 이미지 전체에서 각각 몇 픽셀인지 센다. **「옛 값 0픽셀」이 판정이고, 사람 눈은 대조군으로만 쓴다.**

```python
from PIL import Image
import collections
im = Image.open(path).convert('RGB')
c = collections.Counter(im.getdata())
# '#%02x%02x%02x' % rgb 로 바꿔 새 값·옛 값 집합과 대조
```

이건 「데이터는 맞는데 렌더가 옛 값」인 경우와 다른 사고다. 그쪽은 렌더가 실제로 낡은 것이고, 이쪽은 렌더도 맞는데 내가 잘못 본 것이다. 증상이 같으니 **먼저 픽셀을 세서 둘을 가른다.**

거대 프레임은 아예 안 잡힌다는 것도 같이 알게 됐다. 19,657×18,798짜리 최상위 프레임은 렌더가 안 나온다.

### 3. 설정값으로 화면 결과를 짐작하지 않는다

사흘에 세 번, 전부 같은 유형으로 넘어졌다. **설정값은 상한이지 현재 상태가 아니다.**

「끝을 잘라 낸다」 설정이 걸려 있고 최대 폭이 245라고 해서 잘리는 게 아니다. 실제 폭이 최대 폭보다 좁으면 아무것도 안 잘린다. 사고 과정 토글의 단계 텍스트를 「최대 폭 245라 웹에서 문구가 절반도 안 보인다」고 보고했는데, 노드를 열어 재니 실제 폭이 그보다 훨씬 좁아서 멀쩡했다.

**노드를 열어 실제 폭·정렬·배경·줄 수를 재면 5분이다.** 값을 읽고 「그러니 이렇게 보일 것」으로 넘어가는 게 더 비쌌다.

### 4. 흐름 스토리는 리사이즈 경로를 안 탄다

리사이즈 복구를 고치고 게시본 두 장으로 대조했다. 뷰포트를 1600 → 1150 → 1600으로 흔들었는데 조각 열다섯 개의 합계 폭이 세 시점 모두 같았다. 「고쳐도 안 고쳐도 똑같다」로 나온 것이다.

원인은 대조에 쓴 스토리에 있었다. 흐름 스토리는 기기 화면을 흉내 내는 **고정 폭 틀**이라, 창을 좁히면 안쪽 화면이 좁아지는 게 아니라 **잘린다.** 부모를 재는 코드가 여기서는 절대 발동하지 않는다.

「안 바뀐다」가 고침이 안 먹은 게 아니라 **그 경로를 안 탄 것**이었다. 판정용 스토리를 따로 만들어서 해결했다.

## 트러블슈팅

**문제**: 화면에 멀쩡히 보이는 버튼을 스크립트가 못 찾는다

- 원인: 한글 정규화가 다르다. 문자열 비교로 찾으면 조용히 실패한다. 같은 배열을 이어 붙여 찍으면 그 글자가 나오는데 검색만 실패해서 「렌더가 안 됐다」로 오진하게 된다.
- 해결: 정규화를 맞추거나, 애초에 **구조로 찾는다.** 클래스나 라벨 속성으로 잡으면 안 걸린다.

**문제**: 측정 스크립트를 임시 폴더에 뒀더니 다른 버전을 잡았다

- 원인: 임시 폴더에 둔 스크립트는 전역에 설치된 것을 잡는다. 워크트리에 깔린 버전과 달랐다.
- 해결: 워크트리를 가리키는 방식으로 불러온다.

```js
import { createRequire } from "node:module";
const req = createRequire("/…/worktrees/<이름>/");
const { chromium, webkit } = req("playwright");
```

- 덧붙임: **크롬만 쓰면 이 문제가 안 드러난다.** 크롬은 시스템 브라우저를 쓰니까 버전이 어긋나도 그냥 돈다. 사파리를 켜는 순간 터진다.

**문제**: 브라우저가 「대상 페이지가 닫혔다」로 끊겼다

- 원인: 브라우저를 연달아 띄우다 생긴 환경 문제였다.
- 해결: 경우마다 브라우저를 새로 띄우고 예외 처리로 감싸면 사라진다. **컴포넌트 결함으로 보고하지 않는다.**

## 결과

- 「비어 보인다」의 판정이 덮임에서 잉크로 바뀌었다.
- 색 판정이 눈에서 픽셀 카운트로 바뀌었다. 옛 값 0픽셀이 통과 기준이다.
- 「설정값으로 짐작하지 말 것」이 규칙으로 올라갔다.
- 리사이즈 판정용 스토리가 따로 생겼다.
- 렌더로 판정할 때의 절차가 워크플로 문서 「로컬 렌더로 판정할 때」 절에 모였다.

## AI가 잘한 것 / 디자이너가 보정한 것

- AI: 잉크와 덮임을 둘 다 재서 두 지표가 반대로 간다는 걸 드러낸 것. 픽셀 카운트 판정법을 만든 것. 리사이즈가 발동 안 하는 이유를 스토리 틀에서 찾은 것.
- 디자이너: 「절반도 안 보인다」는 보고를 받고 실물을 열어 아니라고 잡은 것. 수치가 개선을 말할 때도 화면을 보고 판단한 것.

## 아쉬운 점 · 리스크

- 잉크 지표가 스켈레톤 회색을 못 잡는다. 로딩 화면의 「비었나」는 여전히 눈이 필요하다.
- 판정 스토리가 따로 생기면서 흐름 스토리와 판정 스토리를 둘 다 유지해야 한다.

## 한 줄 평

눈으로 본 것을 수치로 바꿀 때, 무엇을 재는지가 어떻게 재는지보다 먼저다. 상자를 재면 상자가 커지고 화면은 그대로다.
