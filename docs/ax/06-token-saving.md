# 06. 코드 줄이기 — 토큰 절약

상태: 진행중 · 기간: 2026-08 ~

## 문제 정의 / 도입 배경

세션이 길어질수록 컨텍스트가 압축되고 초반 판단이 흐려진다. 토큰이 어디서 새는지는 재기 전엔 몰랐다. 「코드를 줄이자」로 시작했는데, 재 보니 코드가 아니라 다른 데서 새고 있었다.

## 목표

- [x] 어디서 새는지 잰다
- [x] 도구를 붙인다 (Headroom)
- [x] 안 쓰는 스킬을 걷어낸다
- [ ] Task Observer 시험 (미착수)
- [ ] 기준선 대비 절감을 다시 잰다

## 사용한 툴

- Claude Code · Headroom(MCP 압축) · 세션 로그

## 작업 과정

### 1단계. 기준선을 쟀다

- 도구별 토큰 비중을 쟀다. Bash 출력이 31.3%로 최대였다. 파일 읽기와 검색 결과가 그다음.
- 코드 자체보다 「명령 출력을 통째로 컨텍스트에 넣는 것」이 컸다.

### 2단계. 압축 도구를 붙였다

- Headroom을 시험 도입했다. 긴 도구 출력을 압축해 넣고 필요하면 되찾는다.
- 대신 압축된 출력은 원문이 아니라서 세부값을 볼 땐 되찾아야 한다. 표 형태 출력이 요약으로 뭉개지는 경우가 있었다.

### 3단계. 안 쓰는 것을 걷어냈다

- 스킬 인벤토리를 정리했다. 안 쓰는 Vercel 계열 99개를 걷어냈다. 스킬 목록도 매 세션 컨텍스트에 실린다.
- 피그마 감사는 페이지 통째 덤프 말고 컴포넌트 단위 스크립트로 쪼갰다. `use_figma` 반환은 15개쯤에서 조용히 잘리기도 해서, 긴 목록은 캔버스에 그려 스크린샷으로 읽는 쪽이 낫다.
- 병렬 팬아웃은 3~4개가 기본. 열 개를 띄웠다가 세션 한도에 걸린 날이 근거다.

## 트러블슈팅

**문제 1**: 「코드를 줄이면 된다」가 틀렸다
- 원인: 재 보니 코드가 아니라 셸 출력이었다.
- 해결: 감으로 줄이지 말고 먼저 어디서 새는지 잰다. 그다음 도구를 고른다.

**문제 2**: 압축된 출력에서 수치가 사라진다
- 원인: 압축이 표를 요약으로 바꾼다.
- 해결: 세부값이 필요한 명령은 파일로 떨어뜨리고 Read로 읽는다. 또는 되찾기로 원문을 본다.

**문제 3**: `use_figma` 출력이 잘린다
- 원인: 반환 크기 제한. 에러 없이 조용히 잘린다.
- 해결: 컴포넌트 단위로 쪼개거나 캔버스에 그려 스크린샷으로 읽는다.

## 결과

- 기준선: Bash 31.3%. Headroom 도입 뒤 절감폭은 아직 다시 재지 않았다. 「줄었다」는 재고 나서만 말한다.
- 스킬 99개 제거, 팬아웃 3~4개 기본, 감사 스크립트 컴포넌트 단위 분할.

## AI가 잘한 것 / 디자이너가 보정한 것

- AI: 도구별 비중을 잰 것. 스킬 인벤토리를 센 것.
- 디자이너: 「코드 줄이기」라는 처음 문제 정의를 「어디서 새나」로 바꾼 것.

## 아쉬운 점 · 리스크

- 압축은 세부값을 잃는다. 검산이 필요한 작업에선 오히려 비용이 될 수 있다.
- 절감 수치를 아직 못 쟀다. 진행중인 이유다.

## 공유할 만한 사항

- 비용은 감으로 줄이지 말고 먼저 어디서 새는지 잰다.
- 긴 출력은 컨텍스트에 넣지 말고 파일로 떨어뜨린다.
- 팬아웃은 3~4개.

## 한 줄 평

「코드를 줄이자」는 문제 정의부터 틀렸다. 재 보니 새는 곳은 코드가 아니었다.
